# 21 — Rebuild From Scratch: Quantalyze v2

*This is a design document, not a rewrite-everything mandate. It is written the way I would actually plan a v2 if Quantalyze's founder handed me the keys today — anchored to what production actually needed (per `02_PRODUCT_ARCHITECTURE.md`), not to a generic "best practices" checklist. Every gap referenced cites the exact finding file. Where the original made a defensible call, v2 keeps it.*

---

## 1. Product requirements (from what shipped, not invented scope)

Quantalyze v1 proved five things a v2 must not regress on (`02_PRODUCT_ARCHITECTURE.md` §1-2, §10): (1) turn an Indian earnings-call PDF into a structured Deep Dive, Delta (QoQ), and multi-quarter Insights brief; (2) self-source transcripts from public filings — zero-friction "type a ticker," no user upload required as the primary path; (3) serve ~200-500 Nifty-tier companies with acceptable latency via parallel LLM calls, not one slow monolithic prompt; (4) monetize both a consumer-facing credit-metered UI and a B2B API-keyed partner product from the *same* underlying analysis cache; (5) degrade gracefully — a single failed section must not sink the whole run. v2 requirements are unchanged in shape, tightened in guarantee: same three pipelines, same self-sourcing ingestion, same dual internal/external API surface, but every one of the above must additionally be *provably* correct (tested), *observable* (metriced), and *safe by default* (authenticated, rate-limited, injection-resistant) — the things v1 explicitly deferred (`19_ARCHITECTURE_DECISION_LOG.md` ADR-01's "cut to what ships, harden later" framing, made good on).

## 2. Domain model

Five aggregates, matching what the JSONB payloads already encode implicitly (`07_DATA_ARCHITECTURE.md` §8) — v2 makes them explicit types, not a byproduct of a Gemini schema:

- **Transcript**: `{ ticker, quarter, sourceUrl, storageKey, pdfHash, ingestedAt }` — identity is `(ticker, quarter)`, content-addressed by `pdfHash` (sha256) so re-ingesting the same file is detected without a full-listing scan (fixes `07_DATA_ARCHITECTURE.md` §7's O(all-files) `resolvePdfKey`).
- **QuarterSnapshot**: one thematic domain's extraction for one ticker/quarter (`sectionName, keyTakeaways[], rawQuotes[]`) — the atomic extraction unit, unchanged from v1's `QuarterSnapshot` (`05_AI_ARCHITECTURE.md` §6).
- **DeltaAnalysis**: aggregate over two `QuarterSnapshot`s → `MetricDelta[]`, `validationScore`, `marketAlignmentPct` — the flagship product entity, keyed `(ticker, qPrev, qCurr)`.
- **InsightsSynthesis**: aggregate over N `QuarterSnapshot`s → `recurringThemes[], guidanceTracks[], credibilityScore`.
- **UsageAccount**: user credits *or* partner API key — same shape (`quotaWindow, used, limit`), unified instead of v1's two independent, differently-raced implementations (`credits.ts` vs `apiAccess.ts`, `08_BACKEND_ARCHITECTURE.md` §10, `20_TECHNICAL_DEBT_AND_GAPS.md` #3/#4).

Company/quarter identity stays a static, versioned registry (v1's `nifty50.ts`/`nifty200.ts` — `07_DATA_ARCHITECTURE.md` §12) — this was the right call, not debt: the Nifty universe changes quarterly at most, and a DB-backed companies table would add a join for no behavioral gain. v2 keeps it, but moves `QUARTERS` (v1's hardcoded array requiring a redeploy to extend, §12) to a computed value derived from the current date plus a grace window, so "what quarters exist" stops requiring a code change.

## 3. System boundaries

Same three-tier shape v1 already has right (`06_AGENT_ARCHITECTURE.md` §6 verdict, `03_SYSTEM_ARCHITECTURE.md`): **Ingestion** (scrape/store, no AI) → **Pipeline** (LLM-function composition, no autonomy needed — see §8) → **API/Frontend** (BFF for the SPA, separate keyed product API for partners). The one boundary v1 blurred that v2 draws sharply: **internal `/api/v1` and external `/api/public/v1` must share one auth/rate-limit middleware chokepoint**, not v1's split where the public surface got real centralized middleware (`08_BACKEND_ARCHITECTURE.md` §9.2) and the internal surface got opt-in per-route auth that 14 of 24 routes simply forgot (§9.1) — same finding as `20_TECHNICAL_DEBT_AND_GAPS.md`'s framing, elevated to an architectural boundary rule: **no route handler is reachable without first passing through a matcher-scoped auth/rate-limit layer**, full stop, enforced by Next.js `middleware.ts`'s matcher covering `/api/:path*`, not `/api/public/:path*` only.

## 4. API design

Fixes the two concrete inconsistencies `08_BACKEND_ARCHITECTURE.md` documents:

- **Versioning** (§2): v1's `"v1"` is a namespace, not a version — no header negotiation, no coexistence path for a hypothetical v2. v2 makes version real but boring: a single `Accept: application/vnd.quantalyze.v1+json`-style header (or, simpler and honestly sufficient at this scale, keep path-prefixed versioning but back it with a **version router** — `app/api/[version]/...` — so a `v2` directory can be added without duplicating every handler, and each handler declares its own DTO version explicitly via the `api-contracts` pattern v1 already proved works for 3 routes (§5) but never extended to the other 21.
- **Auth consistency** (§9): every route — internal and external — goes through one `withAuth(handler, { required: boolean, scopes?: string[] })` wrapper. The four v1 routes that burn real Gemini/scraping budget with zero auth (`seed-analysis`, `seed-transcripts`, `calendar/seed`, `sectors/seed`) become `withAuth(handler, { required: true, scopes: ["admin"] })` — v2 adds the role concept v1 never had (§9.3: "no admin/user distinction anywhere"). `DELETE /api/v1/kpis`'s "wipe everything with a bare DELETE, no auth, no confirmation" (§1, §9.1) becomes `DELETE /api/v1/kpis?scope=<ticker>` with a required admin scope and a mandatory confirmation token — narrow-by-default, not collection-wide-by-default.
- **Response envelope**: one shared `{ data, error, meta }` shape and one `badRequest()`/`domainError()` helper (v1's `lib/services/errors.ts` hierarchy, §4, extended app-wide instead of scoped to 3 routes) — kills the `{detail}` vs `{error}` inconsistency and the arbitrary 400-vs-422 split (§1).
- **Idempotency**: `POST /api/v1/analyze` takes an `Idempotency-Key` header (or derives one from `(ticker, qPrev, qCurr, userId)` server-side) and locks the run via a Postgres advisory lock for its duration — fixes the double-click-costs-2x-credits race (§18) at the API layer, not just the cache layer.

## 5. Data model

Directly closes `07_DATA_ARCHITECTURE.md`'s three concrete gaps:

- **Missing indexes/constraints**: `analysis_results` and `solo_analysis_cache` get a real `UNIQUE(company_ticker, q_prev, q_curr)` / `UNIQUE(ticker, quarter)` constraint from day one, backing `INSERT ... ON CONFLICT DO UPDATE` instead of v1's unwrapped DELETE-then-INSERT (§6, §4's "zero indexes beyond the surrogate PK" finding) — every cache table in v2 follows the pattern v1's *other* seven tables already correctly use (`kpi_snapshots`, `insights_cache`, `concall_links`, `promoter_activity`, `earnings_calendar` all got this right; only the two highest-traffic tables didn't).
- **RLS gap**: v1's Postgres migration script actively *strips* `ENABLE ROW LEVEL SECURITY` because Azure Postgres has no `auth.uid()` (§0) — v2 doesn't try to resurrect Supabase-style RLS on Azure Postgres (that would mean re-adopting Supabase or hand-rolling `SET LOCAL app.user_id` + policies referencing a session variable, real but nontrivial engineering). Instead: v2 accepts application-layer isolation as the real, permanent design (not a stopgap) but backs it with a **compile-time-enforced repository pattern** — every user-scoped repository method's signature *requires* a `userId` parameter (no optional/omittable variant), and a lint rule (`eslint-plugin-security`-style custom rule or a simple `ts-morph` CI check) fails the build if any SQL string touching a `user_*` table lacks a `user_id =` predicate. This turns "every repository method remembers its WHERE clause" (§0's stated risk) from a code-review discipline into a CI gate — cheaper than re-plumbing RLS, and closes the actual risk (a missed filter shipping unnoticed) rather than the symbolic one (not having RLS at all).
- **JSONB, kept**: v1's choice of JSONB over full normalization for pipeline output (§8) was correct and stays — the payload shape is genuinely variable-arity and query patterns are always whole-document fetch-by-key, never partial-field SQL access. v2 adds one thing v1 lacked: a **JSON Schema stored alongside each payload version** (a `schema_version` column + a versioned JSON Schema file per version) so a future field-shape change doesn't silently break `getCachedAnalysis`'s ad hoc `Array.isArray` gatekeeping (§7) — old cached rows either validate against their recorded schema version or get treated as a miss, deterministically, not via a hand-maintained `if (!Array.isArray(...))` guard per field.

## 6. Ingestion architecture

Keeps v1's core insight — scrape screener.in + BSE, no vendor API, no manual upload as the primary path (`07_DATA_ARCHITECTURE.md` §1) is a legitimate zero-friction product choice, not a shortcut — but fixes three real bugs: (1) **de-duplicate the fetcher module for real** — v1's `lib/transcript-fetcher.ts` claims to be "extracted for reuse" but `request/route.ts` keeps its own drifted copy with different lookback windows and PDF caps (§1, §9) — v2 has exactly one ingestion module, imported, not copy-pasted; (2) **content-addressed storage** (§2's domain model) replaces filename-based dedup, so a byte-identical re-upload under a different inferred quarter name doesn't silently create a duplicate; (3) a **confidence-scored quarter inference** — v1's cascade (filename timestamp → PDF-text regex → HTML-context regex, §1) is good design but returns no confidence signal; v2 has it return `{ quarter, confidence: "high"|"low", source }` and routes low-confidence inferences to a small human-review queue rather than silently persisting a guess, given a wrong quarter label silently corrupts every downstream cache key.

## 7. AI architecture

Directly closes the three gaps the assignment calls out (`05_AI_ARCHITECTURE.md`, `11_PRODUCTION_ENGINEERING.md`):

- **No retries** (`05_AI_ARCHITECTURE.md` §11, `11_PRODUCTION_ENGINEERING.md` "Reliability"): v2's `invokeStructured<T>()` — now genuinely shared across all five pipeline files instead of duplicated five times (`20_TECHNICAL_DEBT_AND_GAPS.md` #9) — wraps every Gemini call with 2 retries, exponential backoff, and **jitter**, retrying only on the error classes worth retrying (429/rate-limit, 5xx, network timeout — not a content-policy block or a malformed-prompt 400). This directly ports the pattern the *archived* prototype already had right (`finance-agent/core/llm.py`'s `max_retries=3` + backoff, cited in `05_AI_ARCHITECTURE.md` §11 and `11_PRODUCTION_ENGINEERING.md`'s "production's resilience regressed relative to the code it replaced") — the single cheapest, highest-leverage fix in this whole document, because the code to copy from already exists in the same repo. Critically, retries respect the per-agent timeout budget (a retry that would blow the 25s window doesn't fire) and use `AbortController`/`signal` so a timed-out call is actually cancelled server-side, not just stopped-awaiting (fixes the "Gemini keeps running after we give up on it" finding, `08_BACKEND_ARCHITECTURE.md` §14).
- **No token accounting** (`05_AI_ARCHITECTURE.md` §8, `11_PRODUCTION_ENGINEERING.md` OBSERVABILITY): every `invokeStructured` call reads `result.response.usageMetadata` (already present on the SDK response object, never read anywhere in v1 — confirmed by grep in both files) and writes `{ promptTokens, candidateTokens, totalTokens, latencyMs, model, callSite }` to a lightweight `ai_call_log` table (append-only, partitioned by day). This turns `TECHNICAL_ARCHITECTURE.md`'s static "~600K tokens, ~$0.03/run" cost estimate (flagged as unverified in `05_AI_ARCHITECTURE.md` §8, `11_PRODUCTION_ENGINEERING.md` COST) into a measured number, and lets the credit-pricing model (`ACTION_COSTS = {delta:3, solo:1, insights:4}`, flat regardless of actual transcript size) evolve toward usage-based pricing if the founder ever wants that — v1's flat pricing was a reasonable v1 simplification, not a mistake, but v2 at least makes the *option* to change it possible by having the data.
- **Prompt injection** (`11_PRODUCTION_ENGINEERING.md` SECURITY, `20_TECHNICAL_DEBT_AND_GAPS.md` #5): raw transcript text stops being interpolated bare into the user prompt. v2 wraps it in an explicit, clearly-delimited block (`<untrusted_transcript>...</untrusted_transcript>`) with a system-prompt instruction that content inside that block is data to extract from, never instructions to follow — the standard, low-cost mitigation the finding itself recommends. v2 adds one more layer the finding stops short of: because output is already schema-constrained (v1's real, load-bearing defense — `responseSchema` bounds the *shape* an injection can corrupt, per `20_TECHNICAL_DEBT_AND_GAPS.md` #5's own observation), v2 adds a cheap **post-hoc substring check** — every `rawQuote`/`keyTakeaway` field must appear (fuzzy-matched, not exact, to tolerate whitespace/OCR noise) as a substring of the source transcript text before being persisted; a quote that doesn't match is flagged `unverified` rather than silently shown as a verbatim citation. This is deliberately *not* an LLM-judge call (that's §10's job) — it's a free, deterministic first line of defense against exactly the failure mode injection could produce (a fabricated but well-formatted quote).

## 8. Agent architecture — does v2 need real agentic tool-calling?

**No, and the honest reason is worth stating precisely, per `06_AGENT_ARCHITECTURE.md`'s own verdict**: the "5 specialist agents" were never agents by the load-bearing definition — no tool selection, no looping, no autonomy over what happens next (`06_AGENT_ARCHITECTURE.md` §1, §6). That was the *correct* architecture for this domain, not a shortfall to fix in v2. Quarterly earnings-delta extraction is a fixed-shape task: five thematic domains, one temporal comparison, three synthesis bullets — the same DAG every single time, for every ticker, every quarter. `06_AGENT_ARCHITECTURE.md` §5's role census makes this explicit: a **Planner** role isn't present in either the production system or the more elaborate archived prototype, and the document's own assessment is that the fixed 5-phase shape is "arguably the *right* choice here, not a gap," because the domain doesn't vary enough per-request to justify dynamic planning. v2 keeps parallel LLM-function composition as the core pipeline architecture, unchanged in kind.

Where v2 *does* add one narrow piece of real tool-use, directly informed by what the archived prototype already proved out and never shipped: the **evaluation judge** (§10) and, optionally, a **live web-search grounding step** for the market-alignment check (v1's `computeMarketAlignment()` only checks stock-price direction, not analyst sentiment) — porting the archived `market_validation.py`'s `types.Tool(google_search=types.GoogleSearch())` pattern (`06_AGENT_ARCHITECTURE.md` §3.1, the one place real tool-use already existed in this codebase, just never in production). This is deliberately scoped to *one* call site with a genuine decision to make ("does this need a web search to corroborate"), not a general-purpose agent framework — adopting LangGraph/CrewAI/an MCP-tool-loop for the core extraction pipeline would be solving a problem this product doesn't have, at real cost (latency, unpredictability, harder-to-audit output) for zero product benefit. If a future feature genuinely needs autonomy — e.g. "research this company's competitive position across N documents I don't know in advance" — that's the moment to reach for real agentic orchestration, and even then, `06_AGENT_ARCHITECTURE.md` §3.5's finding that the *only* genuine agentic surface in the whole repo (`finance-agent/mcp_server.py`'s MCP tool exposure) puts autonomy in an external client, not in this codebase's own orchestration code, is the right model: expose the pipeline's functions as tools an external LLM client can call, rather than building an in-house agent loop to call them internally.

## 9. Retrieval — would v2 add RAG?

For most of the product, no — and precisely for the reason `05_AI_ARCHITECTURE.md` §5 and §11 document: v1's "context construction" is full-transcript truncation (120K chars) into every thematic call, and that works because a single earnings call transcript is small enough to fit in context wholesale; there is no multi-document corpus to search *within* a single Delta Analysis run. Adding a vector DB to re-solve a problem that doesn't exist (retrieving from a corpus of one document) would be exactly the kind of "genuinely more trustworthy pipeline" upgrade `06_AGENT_ARCHITECTURE.md` §5's Critic-role analysis warns against reaching for reflexively.

**The one place RAG earns its keep, and it's specific**: quote-accuracy verification against source PDFs — precisely the gap the archived prototype's `judge_evaluator.py`'s `validate_change()` stage already demonstrated a concrete need for (`05_AI_ARCHITECTURE.md` §Archived Prototype, `12_AI_EVALUATION.md` §1.2 stage 2: "Verify both quotes actually appear in their respective source texts or are close paraphrases" — the exact hallucination check production's `localValidation()` structurally cannot do, per `06_AGENT_ARCHITECTURE.md` §5's Critic row). This is retrieval in the narrow, precise sense: given a `rawQuote` string, retrieve the transcript span it's supposedly drawn from and confirm semantic (not just substring) equivalence. v2 implements this as a **lightweight embedding index scoped to one transcript at a time** — embed the current transcript's paragraphs (Gemini's own embedding endpoint, `models/gemini-embedding-001`, already proven out in the archived prototype's `core/embeddings.py`, `05_AI_ARCHITECTURE.md` §12) into an ephemeral in-memory or `pgvector` index built fresh per pipeline run and discarded after, not a persistent cross-document corpus — because the retrieval unit is "verify this quote against *this* transcript," never "search across all transcripts ever ingested." A persistent, cross-transcript vector store (closer to what the archived `finance-agent/core/vector.py`'s FAISS index attempted) would only be worth building for a genuinely different feature — e.g. "find every company that discussed supply-chain risk this quarter" — which is not in v1's proven product scope (`02_PRODUCT_ARCHITECTURE.md` §2's route inventory has no cross-transcript semantic search feature) and should not be built speculatively.

## 10. Evaluation — a real design, built on `judge_evaluator.py`

`12_AI_EVALUATION.md` §0's verdict stands as the reason this is necessary: v1 has zero automated quality evaluation of Gemini's output in production — `responseSchema` is a shape guarantee, `localValidation()` is an internal-consistency arithmetic check, neither can catch a confidently, consistently wrong extraction. v2's design, concretely (following `12_AI_EVALUATION.md` §4's own proposal, which this document adopts rather than re-deriving):

1. **Golden set** (§4.1): seed from the 10 real transcripts already sitting in `finance-agent/multiagent_analysis/all-pdfs/` — five already form adjacent-quarter pairs (Bajaj, HDFC, Bharti, SBI, ICICI) matching the exact `(ticker, qPrev, qCurr)` shape `POST /api/v1/analyze` needs. Run Delta Analysis once per pair, human-annotate the expected `DashboardPayload` (expected signal, expected metrics with source-quote references) — zero new data-sourcing cost, reusing what's already in the repo.
2. **Regression suite** (§4.2): a scheduled CI job that re-runs `runPipeline()` directly against the golden set on every prompt/schema change, diffing structured fields exact-match (`overallSignal`, a closed enum) or numeric-tolerance (`signalScore`, ±0.5) — catches prompt-edit regressions before they ship, at zero incremental Gemini-judge cost for the exact-match fields.
3. **LLM-as-judge** (§4.3): port `judge_evaluator.py`'s four-stage taxonomy (extraction quality → change/quote-accuracy → signal-classification correctness → verdict coherence) from LangChain/Python to the `@google/generative-ai` SDK already used everywhere in `lib/`, mapped onto Quantalyze's actual pipeline stages (table in `12_AI_EVALUATION.md` §4.3). Critically, **not** a same-family-judge-only design: v2 uses a *different* model family for the judge than the generator (e.g. Claude or GPT-4o-class judging Gemini output) specifically to avoid the archived version's own unaddressed weakness — a same-family judge (Gemini judging Gemini, `12_AI_EVALUATION.md` §1.1) shares blind spots with the generator. Run as an **opt-in async job**, exactly as the archived version did (`--evaluate` flag, §1.5) — never synchronously blocking the 300s-budgeted user-facing request — against the golden set on every change, and sampled (e.g. 2-5%) against real production runs continuously, writing scores to a queryable table (not the archived version's flat JSON/markdown files, `12_AI_EVALUATION.md` §4.3) so score trends are visible per-ticker and per-pipeline-version over time.
4. **Human feedback loop** (§4.5): a thumbs-up/down + note on every Delta Analysis result, written to an `analysis_feedback` table — the cheapest mechanism, and the only one that surfaces real production edge cases no synthetic golden set anticipates, becoming a second, more-trustworthy-than-same-family-judge golden set over time.

## 11. Frontend

`09_FRONTEND_ARCHITECTURE.md`'s two headline gaps get fixed directly, not reframed:

- **Accessibility-zero** (§ accessibility grep: zero `aria-`, zero `alt=`, zero `role=` across the entire `app/`+`components/` tree): v2 treats this as a build-time gate, not a backlog item — `eslint-plugin-jsx-a11y` runs in CI as a blocking check from day one (v1 had *no* lint gate in CI at all, `14_DEVOPS_CLOUD.md` §5.3's "only gate is does it build"), every `lucide-react` icon used as an interactive control gets an explicit `aria-label`, every data-bearing image/chart gets alt text or an `aria-describedby` summary, and the streaming `AgentPanel` progress UI — which is pure visual animation in v1 — gets an `aria-live="polite"` region so a screen-reader user actually hears "Revenue & Growth: done" the way a sighted user sees it, which is a genuinely free accessibility win given the NDJSON progress events already carry that exact information (`05_AI_ARCHITECTURE.md` §10).
- **No error boundaries** (§6: zero `error.tsx` files under `app/`, a thrown render error surfaces Next.js's default error screen): v2 adds a route-level `error.tsx` for every data-bearing route, using Next.js's built-in App Router convention v1 simply never adopted — cheap, framework-native, no library needed. Paired with this: v1's flat-string error state (`error: string | null`, no taxonomy, `09_FRONTEND_ARCHITECTURE.md` §6) becomes a typed `{ kind: "network"|"auth"|"quota"|"pipeline"|"unknown", message, retryable: boolean }` shape, so the UI can offer a real "retry" affordance specifically when `retryable: true` rather than a dead-end red box.
- **Kept, deliberately**: v1's decision to make Server Components auth-gate-only and push all data-fetching client-side (§1) is *not* rewritten to force SSR data-fetching — for a dashboard this personalized and this frequently-changing (per-request cache checks, credit balances), client-side fetch-on-mount is a reasonable choice, and forcing it into RSC data-fetching would add complexity (streaming Suspense boundaries per data dependency) without a clear product win. v2 does fix the *inconsistency* v1 has (three of nine data routes skip server-side auth gating entirely, §1) — every route gets the same server-side `getCurrentUser()` redirect, uniformly.
- **Also fixed, smaller**: the two unsynced watchlist systems and two unsynced PDF-export code paths (`02_PRODUCT_ARCHITECTURE.md` §9, `09_FRONTEND_ARCHITECTURE.md` §3) collapse into one `useWatchlist()` hook shared via a proper `hooks/` module (v1 had zero shared hooks directory, §5) backed by the server (`user_tickers`) with `localStorage` purely as an offline-first cache layer in front of it, not a second, unsynced source of truth.

## 12. Observability

Currently entirely absent per `11_PRODUCTION_ENGINEERING.md` OBSERVABILITY (no metrics library, no `/metrics` endpoint, `/api/health` is a static `{status:"ok"}` with no dependency check, no tracing, no AI telemetry). v2 design:

- **Structured logging**: replace all 65 `console.*` call sites (`08_BACKEND_ARCHITECTURE.md` §13) with a single logger (pino — lightweight, Node-native, works fine in a Container Apps context) emitting JSON with a `requestId` propagated end-to-end. v1 already proved the *pattern* works well in exactly one place — `middleware.ts`'s structured `log()` helper with `crypto.randomUUID()` request IDs (§13) — v2 just extends that one good implementation app-wide instead of leaving it scoped to the low-traffic public API.
- **Metrics**: Prometheus-format `/metrics` endpoint (or Azure Monitor SDK, given the Azure-native stack) exporting per-pipeline latency histograms, per-agent success/failure counters, cache hit/miss ratios, and credit-deduction counts — the concrete numbers `TECHNICAL_ARCHITECTURE.md`'s cost/latency claims currently assert without measurement (`11_PRODUCTION_ENGINEERING.md` PERFORMANCE, OBSERVABILITY).
- **AI telemetry**: the token/latency logging from §7 feeds directly into per-call and per-pipeline dashboards — "what % of Delta Analyses had at least one failed thematic agent this week," a question v1's own docs note is currently unanswerable without grepping raw container logs by hand (`11_PRODUCTION_ENGINEERING.md` OBSERVABILITY).
- **Real health check**: `/api/health` in v2 actually checks Postgres connectivity and a cheap Gemini reachability probe (with a short timeout, so a slow Gemini doesn't fail the liveness check outright — distinct from readiness) — v1's static `{status:"ok"}` (deliberately minimal per its own design doc, to avoid flapping on transient external blips, `14_DEVOPS_CLOUD.md` §5.5) was a reasonable choice for a *liveness* probe but the product needs a *separate* readiness endpoint that does check dependencies, gated into the deploy pipeline (§14).
- **Tracing**: OpenTelemetry, exporting to Azure Application Insights (already provisioned once in v1's App Service era per `14_DEVOPS_CLOUD.md` §6, then apparently dropped in the undocumented Container Apps jump) — spans across the ingestion → pipeline → persistence chain so a slow Delta Analysis is diagnosable by which phase, not just "it was slow."

## 13. Security

Every finding cited in `08_BACKEND_ARCHITECTURE.md`/`11_PRODUCTION_ENGINEERING.md`/`20_TECHNICAL_DEBT_AND_GAPS.md` gets a specific fix, not a general "add security":

- **14/24 unauthenticated routes** (`08_BACKEND_ARCHITECTURE.md` §9.1): closed by §3's boundary rule — a matcher-scoped middleware covering all of `/api/*`, with an explicit `public: true` opt-out a route must declare (inverting v1's implicit-opt-in-to-auth default to an implicit-opt-in-to-public default, which fails safe instead of failing open).
- **Prompt injection** (`11_PRODUCTION_ENGINEERING.md` SECURITY, `20_TECHNICAL_DEBT_AND_GAPS.md` #5): §7's delimiter-wrapping + post-hoc quote-substring check.
- **RLS gap** (`07_DATA_ARCHITECTURE.md` §0, `11_PRODUCTION_ENGINEERING.md` SECURITY): §5's CI-enforced `WHERE user_id` lint gate, an honest replacement for RLS given the Azure Postgres connection model rather than a doomed attempt to resurrect Supabase-specific policies.
- **Credits race condition** (`07_DATA_ARCHITECTURE.md` §10a, `20_TECHNICAL_DEBT_AND_GAPS.md` #3, `11_PRODUCTION_ENGINEERING.md` SCALABILITY): fixed with the exact atomic-`ON CONFLICT`-increment pattern v1's own `apiAccess.ts` already proved out for the *other* metering system (`08_BACKEND_ARCHITECTURE.md` §6's "a rare, well-documented example of the Postgres migration being used to fix a known correctness bug") — `UPDATE user_credits SET used = used + $1 WHERE user_id=$2 AND month=$3 AND used + $1 <= quota RETURNING used`, one atomic round trip, no read-then-write window. v2 also unifies this with the public-API quota check (§2's `UsageAccount` aggregate) so the fix is written once, not twice independently (as `20_TECHNICAL_DEBT_AND_GAPS.md` #4 recommends).
- **Dependency scanning**: Dependabot + `npm audit --audit-level=high` as a CI gate — absent entirely in v1 (`11_PRODUCTION_ENGINEERING.md` SECURITY).
- **Kept, correctly**: v1's OIDC federated-credential GitHub Actions auth (no long-lived Azure secret, scoped to `repo:.../ref:refs/heads/main` only, `14_DEVOPS_CLOUD.md` §5.2) and its SHA-256 API-key hashing (`08_BACKEND_ARCHITECTURE.md` §10b) are both genuinely correct security engineering — v2 keeps both unchanged.

## 14. Deployment — would I keep Container Apps?

**Yes** — and this is worth being precise about, because the interesting question here isn't the destination, it's the process gap. Container Apps (over App Service) is the right target for this workload shape: the app is stateless (`11_PRODUCTION_ENGINEERING.md` SCALABILITY confirms this holds), needs to scale out under bursty concurrent-pipeline load, and Container Apps' revision-based, Kubernetes-backed model gives real traffic-splitting/canary primitives App Service's slot model approximates less cleanly. v1 landed on the right infrastructure.

**But the *process* by which it got there is a real, specific failure, not a nitpick**: `14_DEVOPS_CLOUD.md` §7 documents an exhaustively detailed, dated design doc and execution record for Vercel → **App Service** — including a written, explicit Out-of-scope line stating "Containerization/Docker... no Dockerfile is needed for this hosting choice" and "Container Apps... Not needed now" — and then the app is, today, running on Container Apps with a Dockerfile, with **zero design doc, zero spec, zero execution record anywhere in the repository** explaining when or why that second migration happened. Every other migration in this codebase (repositories, data+storage, auth) got the same disciplined treatment: a dated design doc, an execution record, a stated safety window, explicit in/out-of-scope sections. This one didn't. **Should it have gone through the same discipline? Unambiguously yes** — not because Container Apps was the wrong choice (it demonstrably wasn't), but because the *reasoning* for reversing a very recently and explicitly stated "not needed now" decision is now unrecoverable from this repository. An engineer debugging a failed deploy today would read the App Service execution record, try App Service-specific `az webapp` rollback commands, and find nothing (`14_DEVOPS_CLOUD.md` §7's stated risk) — this is not a hypothetical, it's the direct, foreseeable consequence of skipping the process on the one migration where the destination changed again within what was presumably a short window.

v2's deployment design, concretely: keep Container Apps, but (1) write the missing retroactive design doc for App Service → Container Apps *now*, closing the documentation gap before it causes an incident; (2) add the test/lint gate `14_DEVOPS_CLOUD.md` §5.3 confirms is entirely absent (`npm ci && npx tsc --noEmit && npm run lint && npm test` before `docker build` even starts — v1's only gate today is "does it build," §10 recommendation #2); (3) add a staging environment — a second Container App + a narrower-scoped OIDC credential (`ref:refs/heads/staging`) — closing §5.1's "every merge to main deploys straight to prod, zero gate" finding; (4) a post-deploy health-gated rollout (poll the new revision's `/api/health` readiness endpoint from §12 before shifting 100% traffic, `14_DEVOPS_CLOUD.md` §10 recommendation #5) with an actual scripted rollback command, not just "the raw material for rollback exists by accident of good SHA tagging" (§5.4); (5) Infrastructure-as-code (Bicep, matching the all-Azure stack) replacing the `az` CLI commands currently recorded only as prose inside markdown plan files (§4) — this alone would have made the undocumented Container Apps jump impossible to make silently, because the IaC diff *is* the migration record.

## 15. Scaling

`11_PRODUCTION_ENGINEERING.md` SCALABILITY's finding stands as the accurate baseline: v1's statelessness is genuinely correct (no in-memory caches, no module-level mutable state in any route or pipeline file, every cross-request concern externalized to Postgres) — this *does* hold up under horizontal scale-out today, and v2 keeps this design principle exactly as-is; it was not a gap. What v2 adds, addressing the two concrete risks the finding names:

- **The credit and API-quota races** (§13, above) get strictly worse under multi-replica scale-out because there's no cross-replica coordination — fixed at the source with atomic SQL, which is replica-count-agnostic by construction (the fix doesn't get harder as replicas increase, unlike a fix that relied on in-process locking would).
- **No worker/queue architecture** (`11_PRODUCTION_ENGINEERING.md` SCALABILITY: "no background job queue... every AI pipeline runs synchronously inside the HTTP request/response lifecycle," which is *why* the 270s in-request timeout exists at all): v2 moves the three AI pipelines off the synchronous request path onto a real queue (Azure Service Bus — already the natural first-party choice for an Azure-native stack, and notably absent from v1 despite running on Azure the whole time, per the same finding). `POST /api/v1/analyze` becomes: enqueue → return a job ID immediately → client polls or reconnects an SSE/NDJSON stream keyed to that job ID for progress. This removes the artificial in-request timeout ceiling entirely (no more nested 270s/300s/55s/25s timeout stack, `08_BACKEND_ARCHITECTURE.md` §14's "three nested timeout layers for one endpoint"), gives real admission control/backpressure under a request burst (bounded by queue depth and worker concurrency, not by however many Container Apps replicas can spin up simultaneously), and — as a direct side effect — fixes the client-disconnect-doesn't-stop-the-pipeline waste (`20_TECHNICAL_DEBT_AND_GAPS.md` #16): a worker checking "is anyone still listening for this job" before starting expensive Gemini calls is a natural fit for a queue-based design in a way it never was for a synchronous request handler.
- **Connection pool sizing** (`11_PRODUCTION_ENGINEERING.md` PERFORMANCE: unconfigured, running at `pg`'s library default of 10 per replica, un-budgeted against Postgres Flexible Server's connection cap): v2 explicitly sets `max` per replica as a function of the planned replica count and the provisioned Postgres tier's connection limit, documented in the IaC (§14) rather than left as an accidental default.

## Which of the original's decisions were good judgment, and which were real mistakes

These are different categories, and conflating them is the single easiest way to sound naive in an interview. **Good judgment** means: given the information and constraints at the time, this was the correct call, and a competent engineer would make it again — the "debt" is deliberate, scoped, and named. **A real mistake** means: the decision wasn't a reasonable trade-off under constraint, it was avoidable at the time it was made, at little or no extra cost, and nobody chose to defer it — it just happened.

**Good judgment, unambiguously**: abandoning the Python multi-agent/RAG "NotionWealth" platform after three weeks of it not shipping anything a user could touch, and rebuilding as a narrower Next.js app with parallel LLM-function composition instead of an agent framework (`19_ARCHITECTURE_DECISION_LOG.md` ADR-01, `QUANTALYZE_ENGINEERING_MASTER_MAP.md` §7) — this is the single best decision in the repo's history, not a compromise. The domain (fixed-shape quarterly extraction) genuinely doesn't need agentic autonomy, `06_AGENT_ARCHITECTURE.md`'s own analysis confirms the fixed-DAG shape is architecturally correct, and v2 keeps it unchanged (§8). Caching via the same Postgres already in use, instead of standing up Redis, was correct — it's the single largest cost lever in the whole system (`11_PRODUCTION_ENGINEERING.md` COST), and a second datastore would have added operational surface for no benefit at this scale. The disciplined, dated, written-design-doc-plus-execution-record Strangler Fig approach used for three of the four major migrations (repositories, data+storage, auth — `19_ARCHITECTURE_DECISION_LOG.md`) is genuinely exemplary process, the kind most startups never bother with pre-revenue. Choosing `responseSchema`-constrained structured output over free-text-then-parse, deferring a full test suite while the product's shape was still being found, and shipping graceful per-agent degradation (null-and-filter) instead of retries under a hard latency budget were all reasonable trade-offs given a 270-second wall-clock ceiling and a pre-launch user base.

**Real mistakes, not prioritization gaps**: the credits race in `credits.ts` is not deferred debt — it's a bug nobody noticed, sitting one file away from the identical bug in `apiAccess.ts` that *was* noticed, documented, and fixed (`07_DATA_ARCHITECTURE.md` §10a, `20_TECHNICAL_DEBT_AND_GAPS.md` #3) — the fix pattern was *already in the same codebase* and simply wasn't applied to its sibling. The undocumented App Service → Container Apps jump is a process mistake, not a scope trade-off: every other migration got a design doc; this one, which reversed an explicitly and recently stated "not needed now" decision, did not, for no evident reason (`14_DEVOPS_CLOUD.md` §7). Fourteen unauthenticated internal routes — four of which can burn real, unbounded Gemini API spend — is not "auth coverage was deprioritized," it's routes that were written assuming obscurity-by-URL as a security model, which was never a deliberate, stated trade-off anywhere in the docs (`08_BACKEND_ARCHITECTURE.md` §9.1's own framing: "written assuming obscurity-by-URL, not actual access control"). Zero accessibility effort and zero prompt-injection mitigation are gaps a five-minute `eslint-plugin-jsx-a11y` install or a one-paragraph prompt change would have closed at negligible cost — these aren't "ship first, harden later," they're costs nobody paid because nobody looked, and the interview-worthy distinction is exactly that: *harden later* implies a plan existed to come back; these had none. The stale README/TECHNICAL_ARCHITECTURE.md describing a system that stopped being true in July 2026 is the same pattern at documentation scale — not a resourcing trade-off, a follow-up step that was simply dropped after every migration that needed it.

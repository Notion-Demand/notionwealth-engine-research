## MY TOP 20 ENGINEERING GAPS

**Ordering logic** (one sentence, as requested): the list is ranked by (Interview importance + Job-market importance) descending, with Difficulty as the tiebreaker so cheaper wins first, except for two deliberate manual reorderings — security/auth is pulled ahead of testing and evaluation because you want to know your security posture before you start instrumenting anything on top of it, and AI observability is pulled ahead of the Azure-AI-service port because the token/latency logging built while closing the observability gap is exactly the tool needed to produce a credible, measured Gemini-vs-Azure-OpenAI comparison rather than a hand-wavy one.

Each row: **Interview (1-5) | Job-market (1-5) | Difficulty (1-5) | Time to close | Can Quantalyze itself close it?**

### 1. Fourteen of 24 internal API routes have zero authentication
**5 | 5 | 1 | 2-3 days | Yes** — add `getCurrentUser()` checks to `GET /api/v1/available`, `/screener`, `/sectors`, `/calendar`, `/divergence`, `/concall`, `/kpis`; add an admin secret header (`x-admin-key` checked against an env var) to the four unauthenticated `*seed*` POST routes and `DELETE /api/v1/kpis`, since those are legitimately ops tooling, not user-facing endpoints (`08_BACKEND_ARCHITECTURE.md` §9.1). This is the single cheapest, highest-leverage fix in the whole list — one day of work closes the most severe finding in the entire technical-debt log (`20_TECHNICAL_DEBT_AND_GAPS.md` treats the sibling doc-drift findings as P0, but this is functionally worse: unauthenticated routes that burn real Gemini spend).

### 2. Zero automated tests anywhere in the live app
**5 | 5 | 2 | 1-2 weeks for a starter suite | Yes** — install Vitest (lowest-friction for a Next.js 14/TypeScript/ESM codebase, per `13_TESTING.md` §4.1), then write unit tests for the pure, deterministic, currently-zero-coverage functions: `lib/divergence-score.ts` (102 lines, pure arithmetic, no LLM, no mocking needed), `localValidation()` and `computeMarketAlignment()` in `lib/pipeline.ts`, and `computeConfidence()` in `app/api/v1/screener/route.ts`. These are exactly the threshold-and-magic-number logic (`-12%` per flag, `0.5` floors, sign-consistency checks) most prone to silent regression when a constant gets tweaked (`13_TESTING.md` §4, `20_TECHNICAL_DEBT_AND_GAPS.md` finding #13).

### 3. No automated evaluation of Gemini output quality
**5 | 5 | 3 | 1-2 weeks using the 10 existing PDFs in `finance-agent/multiagent_analysis/all-pdfs/` | Yes** — this is the gap most directly relevant to a "Senior AI Engineer" title specifically, not generic software engineering. Production has JSON-shape enforcement and one internal-consistency check, and nothing else; a real four-stage LLM-as-judge harness exists but only in the archived Python prototype, never wired into `lib/pipeline.ts` (`12_AI_EVALUATION.md` §0-1). Concrete exercise: `finance-agent/multiagent_analysis/all-pdfs/` already contains 10 real transcripts in exactly the `{TICKER}_{Quarter}.pdf` naming convention `lib/pipeline.ts`'s `resolvePdfKey()` expects, including 5 adjacent-quarter pairs (`Bajaj_Q1_2026`/`Bajaj_Q2_2026`, `HDFC_Q2_2026`/`HDFC_Q3_2026`, `Bharti_Q2_2026`/`Bharti_Q3_2026`, `SBI_Q3_2025`/`SBI_Q4_2025`, `ICICI_Q4_2025`/`ICICI_Q1_2026`) — upload these to Azure Blob, run Delta Analysis on each pair through `lib/pipeline.ts` directly, hand-annotate the resulting `DashboardPayload` as a golden set, and diff future runs against it field-by-field (exact match on `overall_signal`'s closed enum, numeric tolerance on scores, `12_AI_EVALUATION.md` §4.1-4.2).

### 4. No AI telemetry — token usage, per-call latency, or failure rate is ever logged
**5 | 4 | 3 | 1-2 weeks | Yes** — the Gemini SDK's response object exposes `usageMetadata` (input/output token counts) and every call site already knows its own wall-clock latency, but nothing reads or logs either anywhere in `lib/*.ts` (`05_AI_ARCHITECTURE.md` §8, `11_PRODUCTION_ENGINEERING.md` Observability). Concrete exercise: extend `invokeStructured()` in each pipeline file (or, better, the shared client built in gap #14) to log `{model, sectionName, latencyMs, inputTokens, outputTokens, success}` as structured JSON per call, and aggregate into a simple per-pipeline dashboard query. This is also the direct prerequisite for making gap #5's Gemini-vs-Azure-OpenAI comparison a measured claim instead of a guess.

### 5. Zero hands-on experience with any Azure AI service (Azure OpenAI, AI Foundry) despite deep Azure platform experience
**5 | 4 | 3 | 1 weekend + polish (3-5 days) | Yes — the single highest-leverage exercise on this entire list** — every Gemini call in production uses `@google/generative-ai` directly; no `@azure/openai` or Azure AI SDK appears anywhere in `package.json` (`15_AZURE_JD_MAPPING.md` §3, "Strength rating: None — be exact about this in interview"). This is the one clean gap between real Gemini AI experience and real Azure platform (Container Apps, Postgres Flexible Server, Blob, Entra ID) experience that the JD mapping identified — closing it converts "zero Azure AI experience" into "I ported a production JSON-schema pipeline from Gemini to Azure OpenAI and can speak to the API differences with a measured comparison." Concrete exercise: provision an Azure AI Foundry project and Azure OpenAI resource, then port `lib/sector-narrative.ts` — the smallest, single-call, non-critical-path pipeline — to call Azure OpenAI instead of Gemini behind an env flag, translating the `SchemaType.OBJECT` schema tree to OpenAI's JSON-schema structured-output format and keeping the exact same downstream contract shape (`15_AZURE_JD_MAPPING.md` §1, §3).

### 6. No retries or backoff on any Gemini call — a regression relative to the code this project replaced
**4 | 4 | 2 | 3-5 days | Yes** — every pipeline file's `Promise.race([model.generateContent(...), timeout])` has zero retry logic; a transient rate limit or network blip permanently loses that section's data for the run. The archived prototype (`finance-agent/vertex.py`) actually did this better, with `max_retries=3` and exponential backoff (`11_PRODUCTION_ENGINEERING.md` Reliability, "the production system's resilience regressed relative to the code it replaced"). Concrete exercise: add a `retryWithBackoff()` wrapper around `model.generateContent()` in the shared LLM client (gap #14), retrying up to 2 times on retriable errors (429, 5xx, network) with exponential backoff, while respecting the existing per-agent timeout budget.

### 7. No Infrastructure-as-Code for the live Azure resources
**4 | 4 | 4 | 1-2 weeks | Yes** — VNet, subnets, Postgres Flexible Server, Storage account, and Container App were all provisioned manually via CLI, explicitly named as an accepted non-goal in the migration specs ("one-time manual/CLI provisioning is proportionate for a single environment at this stage" — `15_AZURE_JD_MAPPING.md` §16). Concrete exercise: write Bicep (native to Azure, lower ceremony than Terraform for a single-cloud setup) codifying exactly what's already running — this is the highest-leverage single artifact to build before an Azure-heavy interview since it's the most obvious, easily-verified gap in an otherwise strong cloud story.

### 8. `checkAndDeduct()`'s credit-deduction race condition (unacknowledged revenue leak)
**4 | 3 | 1 | 1-2 days | Yes** — `lib/credits.ts` does a read-then-write (`getCreditStatus` then `setUsed(userId, month, status.used + cost)`) with no atomicity; two concurrent requests can both read the same `used` value and one write clobbers the other, silently undercharging (`20_TECHNICAL_DEBT_AND_GAPS.md` finding #3, P0). Concrete exercise: replace with one atomic `UPDATE user_credits SET used = used + $1 WHERE user_id = $2 AND month = $3 RETURNING used`, matching the pattern already correctly applied in the sibling `apiAccess.ts` repository's `incrementUsage` — the fix is already proven elsewhere in the same codebase, it just wasn't ported. Pair with a concurrency test (gap #2) that spins N parallel `checkAndDeduct` calls and asserts the total deducted equals `N × cost`.

### 9. No CI gate that actually runs tests, type-checks, or scans dependencies
**4 | 4 | 1 | 2-3 days | Yes** — `.github/workflows/deploy-azure.yml` runs `npm ci` + `npm run build` and pushes straight to production; no `tsc --noEmit` step, no test step (until gap #2 exists), no `npm audit`/Dependabot (`11_PRODUCTION_ENGINEERING.md` Security, `15_AZURE_JD_MAPPING.md` §14/§18). Concrete exercise: add a `verify` job before the `build-and-deploy` job — `tsc --noEmit`, `npm test`, `npm audit --audit-level=high` — gating the deploy on all three passing.

### 10. No prompt-injection mitigation on scraped, untrusted transcript text
**4 | 3 | 2 | 3-5 days | Yes** — raw transcript text from Screener.in/BSE scraping is interpolated directly into every Gemini prompt with no delimiter escaping and no instruction-hierarchy framing; a successful injection would be silently indistinguishable from a legitimate extraction since the output is still schema-valid JSON (`11_PRODUCTION_ENGINEERING.md` Security, `20_TECHNICAL_DEBT_AND_GAPS.md` finding #5, P1). Concrete exercise: wrap transcript content in an explicit delimited block (e.g. `<TRANSCRIPT>...</TRANSCRIPT>`) with a system-prompt instruction to treat everything inside it strictly as data, and add a cheap regex heuristic scan for injection-shaped phrases ("ignore previous instructions," imperative language addressed to "the AI") that flags — doesn't block — a transcript for manual review before it reaches the five thematic agents.

### 11. No RAG anywhere in the live product
**3 | 4 | 4 | 1-2 weeks for a meaningful demo | Yes** — genuine RAG (FAISS + Gemini embeddings + augmented prompting) exists only in the archived `finance-agent/` prototype; production sends the full truncated transcript to every call with no retrieval step (`05_AI_ARCHITECTURE.md` "Archived Prototype," `19_ARCHITECTURE_DECISION_LOG.md` ADR-09). This was a reasoned decision, not an oversight — full-context is cheap enough at Gemini Flash Lite pricing that retrieval wouldn't move unit economics — but "I can explain why I didn't build RAG" is weaker in an interview than "I can explain why I didn't build RAG *and* I've since built a small, real one." Concrete exercise: a chat-style Q&A feature over a ticker's already-cached `insights_cache`/`analysis_results` payloads using `pgvector` (already Postgres, no new infra) — small, honestly scoped, and directly demoable, not a rebuild of the archived platform's ambition.

### 12. `analysis_results` — the single most heavily-queried table — has zero index beyond its primary key
**3 | 3 | 1 | half a day | Yes** — every cache-hit lookup, every screener load, and every sector-narrative sampler call filters on `(company_ticker, q_prev, q_curr)` or `company_ticker` alone with no composite index backing either, meaning a sequential scan on the hottest read path in the product (`07_DATA_ARCHITECTURE.md` §4, `11_PRODUCTION_ENGINEERING.md` Performance). Concrete exercise: `CREATE INDEX idx_analysis_ticker_quarters ON analysis_results(company_ticker, q_prev, q_curr)` plus a supporting index on `company_ticker` alone, as migration `012_analysis_indexes.sql` — cheap, mechanical, and a good "I found and fixed a real perf bug" interview story.

### 13. The public API's rate-limiter has the same read-then-write race as gap #8, in the opposite direction
**3 | 3 | 1 | 1 day | Yes** — `middleware.ts`'s `getUsageToday` + `incrementUsage` is explicitly self-documented as "best-effort... not atomic" (`20_TECHNICAL_DEBT_AND_GAPS.md` finding #4, P1) — the underlying SQL write is already atomic (`ON CONFLICT ... DO UPDATE SET request_count = request_count + 1`) but the 429 check itself reads a stale value first, so concurrent requests can briefly burst past a partner's daily quota. Concrete exercise: extract the atomic-`ON CONFLICT`-plus-conditional-check pattern from gap #8's fix into one shared helper (`incrementIfUnderLimit(table, key, limit)`) and use it in both places — a clean two-for-one refactor once gap #8 is done.

### 14. `getGenAI()` is copy-pasted near-verbatim across 5 files with no shared LLM client
**3 | 3 | 2 | 3-5 days | Yes** — `lib/pipeline.ts`, `lib/solo-pipeline.ts`, `lib/insights-pipeline.ts`, `lib/sector-narrative.ts`, `lib/kpi-extractor.ts` each construct their own `GoogleGenerativeAI` instance, and they already disagree on missing-key behavior (a hard `throw` in some, a silent `console.warn`-and-skip in others — `19_ARCHITECTURE_DECISION_LOG.md` ADR-03, `20_TECHNICAL_DEBT_AND_GAPS.md` finding #9, P2). Concrete exercise: extract `lib/llm/client.ts` mirroring the composition-root pattern already proven for the database layer (`lib/repositories/index.ts`) — one `getGenAI()`, one `invokeStructured<T>()` with consistent error handling, retry (gap #6), and telemetry (gap #4) built in once. This is scaffolding gap #5's Azure port sits on top of, but is independently valuable and doesn't block it.

### 15. No user-feedback signal on any AI output — no thumbs-up/down, no engagement tracking of any kind
**3 | 3 | 2 | 3-5 days | Yes** — `grep` for any analytics SDK or click-tracking returns zero hits; `app/privacy/page.tsx` states outright "we do not use third-party analytics trackers" (`16_ONELEET_JD_MAPPING.md` "Feedback loops," `12_AI_EVALUATION.md` §4.5). Concrete exercise: a lightweight thumbs-up/down plus optional note on each Delta Analysis result in `DashboardClient.tsx`, written to a new `analysis_feedback` table keyed the same way as `analysis_results` — cheap, and becomes a second, human-labeled golden set over time, independent of and more trustworthy than the same-family LLM-judge approach in gap #3.

### 16. Service-layer pattern exists but is adopted by only 3 of 24 routes
**3 | 3 | 3 | 1-2 weeks | Yes** — `lib/services/` (a real, dependency-injected `SectorThesisService` plus a clean error-class hierarchy) is used exclusively by the 3 public-API routes; every internal route, including the flagship `app/api/v1/analyze/route.ts`, calls repositories directly with cache/credit/orchestration logic inline (`08_BACKEND_ARCHITECTURE.md` §4, `20_TECHNICAL_DEBT_AND_GAPS.md` finding #8, P2). Concrete exercise: extract an `AnalysisService` wrapping the cache-check → credit-check → pipeline-run → save sequence currently inline in `analyze/route.ts`, matching the codebase's own stated architecture principle ("routes stay thin... no business logic in a route file").

### 17. No model routing — every task, from a 0-10 evasiveness score to full thematic extraction, uses the same model
**2 | 3 | 1 | 2-3 days | Yes** — `gemini-2.5-flash-lite` is hardcoded across all five AI-calling files with no cheaper/faster model substituted for lightweight sub-tasks (`05_AI_ARCHITECTURE.md` §12, `11_PRODUCTION_ENGINEERING.md` Cost). Concrete exercise: route the evasiveness scorer and the sector-narrative call to a smaller/cheaper model tier, and measure the actual cost delta using gap #4's telemetry — a small, concrete "I did tiered model routing and measured the savings" story.

### 18. Zero accessibility effort across the entire application
**2 | 3 | 3 | 1-2 weeks for a meaningful pass | Yes** — exhaustive greps for `aria-`, `alt=`, `role=` return zero hits anywhere in `app/` or `components/`; the live-updating `AgentPanel` progress UI has no `aria-live` region at all (`09_FRONTEND_ARCHITECTURE.md` §14). Concrete exercise: an `aria-live="polite"` region on `AgentPanel.tsx`'s status changes and a real ARIA combobox pattern (`role="combobox"`, `aria-expanded`, `aria-activedescendant`) on `DashboardClient.tsx`'s `CompanySearch` — the two highest-traffic interactive surfaces, not a full-app pass.

### 19. Dead `Supabase*Repository` classes and stale top-level docs, past their own documented cleanup deadline
**2 | 2 | 1 | 2-3 days | Yes** — every repository file still carries a full, unused `Supabase*Repository` implementation months past the migration spec's own stated deletion criteria, and `README.md`/`TECHNICAL_ARCHITECTURE.md`/`.env.local.example` still describe the pre-migration Supabase-only stack (`07_DATA_ARCHITECTURE.md` §0, `20_TECHNICAL_DEBT_AND_GAPS.md` findings #1, #7, both P0/P1 for documentation-trust reasons). Concrete exercise: delete the 12 dead `Supabase*Repository` classes and `lib/supabase/admin.ts`, then regenerate `README.md`/`TECHNICAL_ARCHITECTURE.md`'s tech-stack sections and `.env.local.example` from the actual `process.env.*` reads in `lib/postgres/client.ts`, `auth.ts`, and `lib/repositories/storage.ts`.

### 20. No client-disconnect cancellation — an abandoned analysis keeps burning Gemini calls server-side
**2 | 2 | 2 | 2-3 days | Yes** — the NDJSON `ReadableStream` has no `request.signal`/`AbortController` wiring into `runPipeline()`; a closed tab or navigation mid-analysis lets up to ~20 Gemini calls complete for a result nobody will see (`20_TECHNICAL_DEBT_AND_GAPS.md` finding #16, P2). Concrete exercise: thread the Next.js Route Handler's `request.signal` through to each Gemini call's `RequestOptions.signal` (the `@google/generative-ai` SDK supports this), so a client disconnect actually stops in-flight and not-yet-started calls.

## THE 90-DAY PLAN

The three phases follow one sequencing principle throughout: **fix correctness and security first, instrument what you can now trust, then spend the instrumented, stable base on the highest-leverage new capability** (the Azure AI service port) **and the product-maturity items an interviewer will probe once the fundamentals are no longer in question.** Each phase closes gaps whose fixes the next phase's work depends on — Phase 2's evaluation harness needs Phase 1's test runner already installed; Phase 3's Gemini-vs-Azure-OpenAI comparison needs Phase 2's telemetry already logging real numbers.

### Phase 1 (Days 1–30): Correctness, security, and a test foundation

**What gets built**: closes gaps #1 (auth), #8 (credits race), #13 (rate-limiter race), #12 (DB index), #2 (test runner + pure-function unit tests), #9 (CI gate), #19 (dead-code and doc cleanup, partial).

**Why this sequencing**: security and financial-correctness bugs (#1, #8, #13) go first because they're both the cheapest fixes on the entire list (Difficulty 1) and the most consequential to leave open — an unauthenticated route that burns Gemini spend or a race condition that leaks revenue is actively getting worse the longer it's live, unlike a missing test suite, which is static risk. Fixing them also produces the first concrete "before/after" story for the concurrency unit tests built in week 2. Testing infrastructure (#2) comes before any AI-specific work in Phase 2 because the golden-set regression suite and the telemetry-comparison work both need a test runner and CI gate already in place — building the eval harness on top of zero test infrastructure would mean building the infrastructure twice.

**Weekly breakdown**:
- **Week 1** — Auth sweep: add `getCurrentUser()` checks to the 7 unauthenticated `GET` routes; add an `x-admin-key` gate to the 4 `*seed*` POST routes and `DELETE /api/v1/kpis`. Add the `analysis_results` composite index (gap #12) as a same-week quick win since it's half a day of work with zero dependencies.
- **Week 2** — Atomic-SQL fixes: rewrite `lib/credits.ts`'s `setUsed` and `middleware.ts`'s rate-limit check-and-increment to use the atomic `ON CONFLICT ... DO UPDATE SET x = x + 1` pattern already proven in `apiAccess.ts`; extract the shared `incrementIfUnderLimit()` helper (closing gap #13 alongside #8).
- **Week 3** — Install Vitest; write unit tests for `lib/divergence-score.ts`, `localValidation()`, `computeMarketAlignment()`, and `computeConfidence()` in `screener/route.ts`; write the concurrency test for `checkAndDeduct()` that proves week 2's fix (N parallel calls, assert total deducted equals `N × cost`).
- **Week 4** — Add the CI `verify` job (`tsc --noEmit` + `npm test` + `npm audit --audit-level=high`) gating `deploy-azure.yml`'s build step; delete the 12 dead `Supabase*Repository` classes and `lib/supabase/admin.ts`; regenerate `README.md`/`TECHNICAL_ARCHITECTURE.md`'s tech-stack tables and `.env.local.example` from the real env-var reads.

### Phase 2 (Days 31–60): AI reliability, telemetry, and evaluation

**What gets built**: closes gaps #14 (shared LLM client), #6 (retries/backoff), #4 (AI telemetry), #10 (prompt-injection mitigation), #3 (golden-set evaluation harness).

**Why this sequencing**: the shared LLM client (#14) comes first because retries (#6) and telemetry (#4) both need one place to live rather than five duplicated copies — building them into the client once, instead of patching five files independently, is the whole point of finally doing the extraction the codebase's own repository-layer pattern already modeled. Retries come before telemetry because you want failure-and-recovery behavior stable before you start trusting the latency/success numbers you're about to log — a retry firing mid-measurement would otherwise look like a slow call, not two calls. Telemetry comes before the evaluation harness because the harness needs to report not just "did the output match the golden set" but "how expensive and how slow was getting there" — and because Phase 3's Azure-OpenAI comparison is only a credible claim if it's built on real numbers this phase produced, not estimates.

**Weekly breakdown**:
- **Week 5** — Extract `lib/llm/client.ts`: one `getGenAI()`, one `invokeStructured<T>()` with consistent error handling; migrate `pipeline.ts`, `solo-pipeline.ts`, `insights-pipeline.ts`, `sector-narrative.ts`, `kpi-extractor.ts` onto it. Add `retryWithBackoff()` (up to 2 retries, exponential, respecting the existing per-agent timeout budget) inside the same client.
- **Week 6** — Add token/latency/success telemetry (`usageMetadata`, wall-clock latency, per-call success/failure) to the shared client, logged as structured JSON; add prompt-injection mitigation (delimited transcript block + heuristic regex scan flagging, not blocking) to the shared prompt-building helper.
- **Week 7** — Build the golden set: upload the 10 `finance-agent/multiagent_analysis/all-pdfs/` transcripts to Azure Blob, run Delta Analysis on the 5 adjacent-quarter pairs through `lib/pipeline.ts` directly (bypassing the HTTP route, same as the route handler does internally, with `force: true`), hand-annotate expected `overall_signal`, key metrics, and earnings-delta bullets.
- **Week 8** — Port `judge_evaluator.py`'s 4-stage taxonomy (extraction quality, change-detection validity, signal-classification correctness, verdict quality) from LangChain/Python to the `@google/generative-ai` SDK already used in `lib/`, scoped to Quantalyze's actual pipeline stages (`runThematicAgent`, `runTemporalDelta`, `runEarningsDeltaAgent`); wire as an opt-in scheduled GitHub Actions job that runs against the golden set and writes scores to a new `evaluation_scores` table, not flat files.

### Phase 3 (Days 61–90): Azure AI service, cloud maturity, and product feedback

**What gets built**: closes gap #5 (Azure OpenAI port — the flagship milestone of this whole plan), #7 (IaC), #11 (RAG demo), #15 (user-feedback loop), #16 (service-layer retrofit), #17 (model routing), #18 (accessibility pass on the two highest-traffic screens), #20 (AbortController wiring).

**Why this sequencing**: this phase exists to close the single cleanest, most-cited gap in the whole case study — real Gemini AI experience plus real Azure platform experience, but zero Azure *AI service* experience (`15_AZURE_JD_MAPPING.md`'s overall verdict: "strong-to-excellent on the Azure platform half of this JD, and essentially zero on the Azure AI services half") — and it's scheduled last, not first, specifically because it needs Phase 1's stable foundation and Phase 2's telemetry to produce a comparison worth presenting rather than a toy port. Everything else in this phase is lower-stakes product/cloud-maturity work that rounds out the story once the flagship exercise is done.

**Weekly breakdown**:
- **Week 9 (the flagship milestone)** — Provision an Azure AI Foundry project and Azure OpenAI resource. Port `lib/sector-narrative.ts` — the smallest, lowest-risk, single-call pipeline — to a parallel Azure-OpenAI-backed implementation behind an env flag, translating its `SchemaType.OBJECT` schema tree to Azure OpenAI's structured-output JSON schema format and keeping the exact same downstream `NARRATIVE_SCHEMA` contract shape. Run both the Gemini and Azure OpenAI versions against the same inputs and use Week 6's telemetry to produce a real, measured latency/cost/output-quality comparison — the artifact that turns "I've never touched Azure AI services" into "I ported a production pipeline and can show you the numbers."
- **Week 10** — Write Bicep for the currently-manually-provisioned Azure resources (VNet, subnets, Postgres Flexible Server, Storage account, Container App) — codify what's already running, not new infrastructure; this is the most obvious, easily-verified remaining gap in an otherwise strong Azure platform story.
- **Week 11** — Ship a small, honestly-scoped RAG demo: chat-style Q&A over a ticker's cached `insights_cache`/`analysis_results` payloads using Postgres `pgvector` (no new infrastructure, reuses the existing database) — closes "no RAG in production" with a real, if deliberately small, shipped feature rather than a rebuild of the archived platform's ambition. Add the `analysis_feedback` thumbs-up/down table and UI in `DashboardClient.tsx` and `EarningsReport.tsx` in the same week, since both are additive, low-risk, and product-facing.
- **Week 12** — Retrofit `AnalysisService` for `app/api/v1/analyze/route.ts` (service-layer consistency, matching the codebase's own stated architecture principles); add model routing for the evasiveness scorer and sector-narrative call to a cheaper model tier, measured against Week 6's telemetry; wire `AbortController`/`request.signal` from the Route Handler into the Gemini SDK calls so a client disconnect actually stops in-flight work; and do a real, scoped accessibility pass — `aria-live` on `AgentPanel.tsx`'s progress transitions, a proper ARIA combobox pattern on `DashboardClient.tsx`'s `CompanySearch` — on the two highest-traffic screens rather than attempting the whole app at once.

**End state after 90 days**: every CANNOT DEFEND item from `23_PROJECT_DEFENSE.md`'s table — Testing, Evaluation, Observability, Customer feedback — moves to at least PARTIALLY DEFEND with real, cited artifacts behind it, Agents and RAG stay honestly labeled but RAG gains one small real production instance, and the single most commonly-probed gap in the Azure Senior AI Engineer JD (zero Azure AI service experience) is closed with a measured, defensible comparison rather than a claim.

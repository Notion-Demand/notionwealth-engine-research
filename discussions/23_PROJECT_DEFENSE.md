# 23 — Project Defense: Can I Credibly Say "I Built an End-to-End AI Product"?

---

## THE QUANTALYZE ENGINEERING STORY

Quantalyze turns Indian earnings-call transcripts into structured investment intelligence. An equity research analyst or PM picks a ticker and a quarter pair, and within about 15–25 seconds gets a "Delta Analysis" — what changed quarter-over-quarter across revenue quality, margins, cost structure, capex, and macro risk, each claim backed by a verbatim quote, classified positive/negative/noise, and cross-checked against how the stock actually moved. There's also a single-quarter "Deep Dive" and a multi-quarter "Insights" synthesis. It's live at quantalyze.demandion.ai, it has real users, and it sells the same intelligence as a metered B2B API to PMS firms and AMCs. The problem it solves is real and unglamorous: reading a 2–3 hour earnings call transcript and extracting the handful of things that actually moved versus last quarter is slow, and doing it consistently across 200 companies every quarter is a job nobody wants to do by hand.

The architecture is shaped the way it is because of a decision I made in my first six weeks. I started in January building something much more ambitious — a Python multi-agent platform, "NotionWealth Intelligence," with a control plane doing task routing, a FAISS vector store for semantic memory, a research-replay engine, and specialist agents for financial/risk/competitive/portfolio analysis. It's still in the repo, frozen, under `finance-agent/` — 15 commits total. By late February it hadn't shipped anything a user could touch, and I made the call to rebuild it as a much leaner Next.js app: instead of an agent framework with autonomy over what to do next, five parallel, schema-constrained calls to Gemini 2.5 Flash Lite per feature, backed by a Postgres cache. That version is what's live today. 159 commits touched `app/`, 89 touched `lib/`. The commit-count asymmetry alone tells the story — I chose the path that reached a customer over the path that was more architecturally interesting. That's the single most important engineering decision in this project's history, and it's the thing I actually learned: recognizing over-scoped ambition early and cutting to what ships is a harder skill than building the ambitious thing in the first place.

The AI pipeline itself is honest about what it is. `lib/pipeline.ts` runs five domain-specialist prompts — Revenue & Growth, Margins & Profitability, Cost Structure, CapEx & Balance Sheet, Macro & Risk — against each of two quarters' transcripts, in parallel via `Promise.all`, each one a single `generateContent` call constrained by a Gemini `responseSchema` so the output is guaranteed-valid JSON, not a fixed prompt with tool-calling or looping. That's ten calls, plus an evasiveness scorer, up to five temporal-delta comparisons, and three synthesis calls — about nineteen Gemini calls per Delta Analysis run. I call these "specialist agents" in the product copy, but I'm careful not to call them agents in an interview: there's no `tools` field anywhere, no branching on what the model decides, no autonomy. It's parallel LLM-function composition with schema-constrained outputs — a legitimate, cost-effective pattern for a domain that doesn't need dynamic planning, but claiming agentic autonomy for it is the easiest thing to get caught overstating.

Data moves through the system in a fairly straightforward line: transcripts get scraped from Screener.in and BSE's announcements API (there's no vendor API for this — it's undocumented endpoints and HTML scraping with spoofed headers), stored as PDFs in Azure Blob, parsed with `pdf-parse` and capped at 120K characters per call, fed into the Gemini calls, and the structured result gets cached in Azure Postgres JSONB tables keyed on `(ticker, quarter-pair)`. Progress streams to the browser as NDJSON — one line per completed agent, not token-level streaming, since there's no single generation to tap in a fan-out pipeline. On a cache hit, none of this runs at all — zero Gemini calls, and the credit system only deducts on a miss, so the caching layer is wired directly into the cost model, not just a read-through convenience.

Where AI connects to product is the credits system: three metered actions (`delta`, `solo`, `insights`) at flat per-action pricing, gating a monthly quota, feeding a public API with hashed keys, per-partner entitlements, and daily quotas. Frontend and backend talk over that NDJSON stream and plain REST otherwise — Next.js 14 App Router, where Server Components exist mostly to do the auth redirect and every Client Component fetches its own data client-side. No global state library, no chart library — every number is a card or a percentage-width div, which is a real gap for a data product but a deliberate one given the scope.

Reliability, evaluation, and observability are where I have to be honest rather than impressive. There are no automated tests anywhere in the live app — zero. Verification is `tsc --noEmit` plus manually clicking through the app, which is explicitly stated in my own migration planning docs, not hidden. There's no LLM-as-judge, no golden dataset, no regression suite checking that a prompt edit didn't degrade output quality — I built a real four-stage LLM-as-judge harness once, in the archived Python prototype, and never ported it to production. What production has instead is a local sign-consistency check (does the score's sign match the label the same model assigned) and a market-price cross-check (does the signal direction match how the stock actually moved) — both real, both useful, neither able to catch a confidently-wrong-but-internally-consistent hallucination. There's no token-usage tracking, no traces, no metrics endpoint beyond a static health check that doesn't actually check any dependency. Fourteen of twenty-four internal API routes have zero auth check, including four that can burn real Gemini spend for anyone who finds the URL. I know exactly where these gaps are because I found most of them writing this case study, not because someone else audited me.

The tradeoffs I'd make differently at scale: I'd stop the Supabase→Postgres migration from leaving dead `Supabase*Repository` classes in every file past their own documented cleanup deadline. I'd fix the two read-then-write credit and rate-limit races with atomic SQL — I already know the fix pattern because I applied it correctly in one repository (`apiAccess.ts`) and forgot to port it to the sibling one (`credits.ts`). I'd add retries with backoff on Gemini calls, since production actually regressed on this relative to the Python prototype it replaced. And I'd close the auth gap on those fourteen routes before anything else, because you want to know your security posture before you start instrumenting observability on top of it, not after.

What I actually learned building this wasn't a specific technique — it was the discipline of shipping the narrower thing. NotionWealth was the more technically interesting system: real RAG, real memory, a real evaluator. Quantalyze is the one that has users, a monetized API, and two subsequent infrastructure migrations driven by real usage and enterprise-sales pressure (Vercel → Azure App Service → Container Apps, Supabase → Azure Postgres/Blob/Entra ID, the second one explicitly because Indian AMC back-office IT is Microsoft-standardized and that matters for vendor security review). Recognizing that the ambitious version wasn't going to ship, and rebuilding around what would, is the actual engineering judgment this project demonstrates — more than any individual pattern inside it.

## Can I credibly say "I built an end-to-end AI product"?

| Dimension | Verdict | Justification |
|---|---|---|
| **Product** | CAN DEFEND | Quantalyze is live at quantalyze.demandion.ai with a coherent, shipped feature set (Delta Analysis, Deep Dive, Multi-Quarter Insights, Screener, KPI Tracker, Promoter Pledge Monitor) and real go-to-market motion — PMS-head conversations directly shaped features like the divergence-score screener (`19_ARCHITECTURE_DECISION_LOG.md` ADR-01, `15_AZURE_JD_MAPPING.md` §2/§22). |
| **Backend** | CAN DEFEND | 24 Next.js route handlers, a real repository pattern with 12 interfaces and a composition root, a genuine service layer for the public API, parameterized SQL throughout, and a documented, executed multi-stage Supabase→Azure Postgres migration verified by row-count-plus-content-hash checks (`08_BACKEND_ARCHITECTURE.md` §3–6, `19_ARCHITECTURE_DECISION_LOG.md` ADR-02/11). |
| **Frontend** | PARTIALLY DEFEND | Next.js 14 App Router with genuinely byte-for-byte incremental NDJSON streaming consumption and real state-machine UX in places — but zero global state management, zero accessibility effort (no `aria-`, `alt=`, or `role=` anywhere), no charting library, and the core authenticated Dashboard screen is effectively desktop-only (`09_FRONTEND_ARCHITECTURE.md` §7, §9, §13–14). |
| **Data** | CAN DEFEND | 13 Postgres tables with JSONB payloads, a real repository abstraction that made a live Supabase→Azure Postgres cutover touch zero route handlers, deliberate cache-key design (the Insights cache's data-derived key auto-invalidates on new transcripts), and Azure VNet-specific connection-resilience tuning discovered from a real production incident (`07_DATA_ARCHITECTURE.md` §0/§6, `11_PRODUCTION_ENGINEERING.md` Reliability). |
| **AI** | CAN DEFEND | Five production pipelines, ~19 Gemini calls per Delta run, Gemini-native `responseSchema` structured-output enforcement (not manual parsing), deliberate per-agent context slicing (first-40K vs last-30K vs full-120K char windows), and cache-before-call logic that eliminates the entire call sequence on a hit (`05_AI_ARCHITECTURE.md` §5–6/§9). |
| **Agents** | CANNOT DEFEND | Every "agent" is a fixed prompt + fixed schema, zero `tools`/`functionDeclarations` anywhere in `lib/` or `app/`, no branching on model output beyond null-filtering after failure. This is parallel LLM-function composition, not multi-agent autonomy — and a real (if narrow) tool-use example exists only in the archived, unshipped prototype (`06_AGENT_ARCHITECTURE.md` §1, §6). |
| **RAG** | CANNOT DEFEND | Zero vector index, embedding store, or retrieval step anywhere in the live product — every call gets the full truncated transcript pasted in, not a retrieval-augmented context. Genuine RAG (FAISS + Gemini embeddings + augmented prompting) exists only in the archived Python prototype and was a deliberate, reasoned decision not to carry forward given the cost/context-window math (`05_AI_ARCHITECTURE.md` "Archived Prototype: Vector Search," `19_ARCHITECTURE_DECISION_LOG.md` ADR-09). |
| **APIs** | CAN DEFEND | A real internal/external API split: 21 session-authenticated internal routes plus a genuinely separate, well-built public partner API with SHA-256-hashed keys, per-key product entitlements, daily quotas, structured request logging, and a domain-error hierarchy — a legitimate B2B API product, not a toy (`08_BACKEND_ARCHITECTURE.md` §2, §9.2). |
| **Cloud** | CAN DEFEND | This is the strongest single dimension: Azure Container Apps, Postgres Flexible Server on a private VNet with no public endpoint, Azure Blob Storage with SAS-token-gated reads, Microsoft Entra External ID via NextAuth, OIDC-federated GitHub Actions CI/CD — executed as a deliberate, staged, spec-documented migration with real production incidents debugged and fixed in code, not tutorial-following (`15_AZURE_JD_MAPPING.md` §16, `19_ARCHITECTURE_DECISION_LOG.md` ADR-07/11). |
| **DevOps** | PARTIALLY DEFEND | OIDC-authenticated container CI/CD to Azure Container Registry is real and correctly done — but there is no test gate in the pipeline, no dependency/vulnerability scanning, no staged rollout (a direct full-traffic `az containerapp update` swap), and the only hosting design docs in the repo describe the *previous* Azure App Service deployment, not the live Container Apps one (`14_DEVOPS_CLOUD.md`, `19_ARCHITECTURE_DECISION_LOG.md` ADR-07). |
| **Testing** | CANNOT DEFEND | Zero automated tests of any kind in the live app — no unit, integration, API, or E2E tests; no test runner is even installed. Verification is `tsc --noEmit` plus manual browser clicking, stated explicitly (not hidden) in the project's own migration planning docs (`13_TESTING.md` §0–1). |
| **Evaluation** | CANNOT DEFEND | Zero automated AI-output quality evaluation in production — no golden dataset, no regression suite, no LLM-as-judge, no human review workflow. A genuinely well-designed four-stage LLM-as-judge harness exists, fully coded, but only in the archived prototype, invoked via an opt-in CLI flag, never wired to the live pipelines, and with no evidence it was ever run (`12_AI_EVALUATION.md` §0–2). |
| **Observability** | CANNOT DEFEND | No metrics library, no traces, no per-call token/latency logging despite the Gemini SDK exposing `usageMetadata` unread. The health check returns a static "ok" with no dependency check. One real exception — structured JSON request logging with a correlation ID — exists only in the public-API middleware, not the high-traffic pipelines where a failure is actually expensive (`11_PRODUCTION_ENGINEERING.md` Observability). |
| **Security** | PARTIALLY DEFEND | The public API's auth (hashed keys, entitlements, quotas) and the Azure networking posture (private VNet, OIDC CI/CD, no long-lived credentials) are genuinely strong — but 14 of 24 internal routes have zero auth check, including four that can burn unlimited Gemini spend for an unauthenticated caller, RLS is not enforced on the live database at all despite the migrations defining it, and there is no prompt-injection mitigation on transcript text sourced from scraped third-party content (`08_BACKEND_ARCHITECTURE.md` §9.1, `11_PRODUCTION_ENGINEERING.md` Security). |
| **Performance** | CAN DEFEND | Extensive, correct use of `Promise.all` fan-out (10+ concurrent Gemini calls per phase), deliberate per-agent context-window scoping to cut token cost, and caching as the dominant, quantified cost/latency lever — a cache hit eliminates ~20 Gemini calls entirely, larger than any model-selection or token-budgeting choice in the system (`11_PRODUCTION_ENGINEERING.md` Performance, Cost). |
| **Product UX** | PARTIALLY DEFEND | Real, deliberate UX work exists — genuinely incremental live-progress streaming, keyboard-driven watchlist cycling with correct closure-stability handling, two distinct client-side PDF export strategies — but there's no skeleton loading, no toast notifications, no route-level error boundaries anywhere, and zero accessibility effort across the entire app (`09_FRONTEND_ARCHITECTURE.md` §6, §14–15). |
| **Customer feedback** | CANNOT DEFEND | No analytics SDK, no click tracking, no "was this useful" signal, no re-run-rate or engagement tracking of any kind — the privacy policy states outright that no third-party analytics trackers are used. Customer-discovery calls with PMS heads are real and did shape the roadmap, but that's a behavioral claim the repo corroborates in spirit, not a code-evidenced feedback loop (`16_ONELEET_JD_MAPPING.md` "Feedback loops," "Work directly with customers"). |
| **Business value** | CAN DEFEND | A documented five-factor feature-evaluation framework (Pain, Innovation, Convenience, Cost, Functional Gap) with explicitly rejected alternatives, real unit economics (~$0.03/Delta run, a stated 95% gross-margin target at 50 users), and a monetized, metered public API with manually-provisioned partner keys — genuine product-engineering judgment tying AI scope to a specific buyer, not building for its own sake (`15_AZURE_JD_MAPPING.md` §2). |

### How to talk about this in an interview

**Lead with, in this order: Cloud, APIs, AI, Data, Backend, Performance, Business value.** These are the dimensions where the evidence is deep and specific — name the exact production incidents (the Entra `oid`-vs-`sub` UUID mismatch, the Azure VNet idle-connection reaping, the App Service `npm start` 503), not just the architecture diagram. "I debugged this in production, here's the fix, here's why it worked" reads as senior-engineer credibility in a way that a clean architecture description alone doesn't. The pivot story (NotionWealth → Quantalyze) is the single best answer to almost any "tell me about a hard decision" question — it's specific, it has real evidence (commit counts, a pivot commit message, a frozen directory), and it demonstrates judgment rather than just execution.

**Own the CANNOT DEFEND items before you're asked, don't wait to be caught.** The move that reads as senior is naming the gap, the reason it's a gap, and what closing it would take — in that order, unprompted, the moment the topic is adjacent. "There's no automated evaluation in production — I built a real four-stage LLM-as-judge harness for the earlier prototype, understand exactly what it would take to port it, and prioritized shipping the pipeline itself first given a two-person budget" is a stronger answer than hoping the interviewer doesn't ask about evaluation. The same move works for Testing ("verification today is `tsc --noEmit` plus manual QA, which is exactly the kind of gap that let two read-then-write race conditions ship undetected — here's what I'd test first and why"), Agents ("I call them agents in the product copy, but they're schema-constrained LLM functions with zero autonomy, and I can draw you the exact line where a real agent architecture would differ"), and RAG ("the production pipeline doesn't do retrieval — full transcripts fit in context at this price point, so RAG would be solving a problem I don't have yet, and I can walk through the math that led to that call").

**Never claim Agents or RAG are in production, even loosely.** These are the two fastest ways to get caught overstating in this specific project, because the honest, precise answer ("LLM-powered function composition, not agents" / "no retrieval in production, real RAG only in an archived prototype") is available, evidenced, and actually makes you look more rigorous than a vague "yes we have agents" would. The interviewer asking a follow-up question you can't answer precisely is far worse than volunteering the precise boundary yourself.

**For Observability, Customer feedback, and Testing specifically — frame as a known-and-prioritized tradeoff, not an oversight.** All three trace back to the same root cause (a pre-launch, largely solo-built product optimizing for shipping speed) and the same fix path (the P0/P1 findings in `20_TECHNICAL_DEBT_AND_GAPS.md` are already written, ranked, and cited — this isn't hand-waving, it's a plan that exists). Say what you'd build first and why: pure-logic unit tests before mocked-Gemini pipeline tests, an atomic-increment fix for the two credit/rate-limit races before anything else, auth coverage on the fourteen open routes before adding observability on top of them. That ordering itself is evidence of judgment, independent of whether the code exists yet.

# Quantalyze — System Architecture

*Repository map, technology stack, and architectural-pattern audit, built by walking the actual tree (`find`, `Glob`, `Grep`) rather than assuming a template. Two systems live in one repo — this file treats them as separate: the **production system** (repo root: `app/`, `lib/`, `components/`, `supabase/migrations/`, `types/`, `public/`) and the **archived prototype** (`finance-agent/`, `disclosure-analysis-pipeline/`, frozen since the Feb 27 2026 "move Next.js app to repo root" pivot commit).*

## A4. Entry points, boundaries, data stores

- **Production entry points**: `app/layout.tsx` + `app/page.tsx` (root Next.js render tree); every `app/api/**/route.ts` is an independent serverless-shaped-but-container-hosted entry point (each exports `GET`/`POST` handlers Next.js dispatches to directly — there is no single "server.ts").
- **Archived entry points**: `finance-agent/main.py` (ad hoc script entry) and `finance-agent/server.py` (FastAPI ASGI app) — two separate, seemingly redundant boot paths, itself a small piece of evidence the prototype's structure was still in flux when development stopped.
- **Backend/frontend separation**: there is **no separate backend service** in production — Next.js Route Handlers under `app/api/v1/**` and `app/api/public/v1/**` are the entire server-side surface, running in the same Docker container/process as the SSR'd pages. `.env.local.example` still lists `NEXT_PUBLIC_API_URL=http://localhost:8000/api/v1` under a "FastAPI Backend" heading — a leftover from when `finance-agent/server.py` *was* the backend the frontend called; nothing in `app/`/`lib/` reads that variable today (confirmed via grep), so it's inert legacy config, not a live boundary.
- **API boundary — `/api/v1/**` vs `/api/public/v1/**`**: `/api/v1/**` is first-party (session-cookie authenticated via `getCurrentUser()`/Auth.js), unversioned in practice (see §B "API Versioning"). `/api/public/v1/**` is the partner-facing developer API, gated by `middleware.ts` (Bearer API key, SHA-256 hashed, checked against `api_keys`/`api_key_products`, per-partner daily quota in `api_usage`), and shaped through the DTO layer in `lib/api-contracts/v1/*.ts`.
- **Data stores**: Postgres (Azure Database for PostgreSQL Flexible Server) is the only structured store — 16 tables total across `supabase/migrations/001-011` (`user_connections`, `analysis_results`, `kpi_snapshots`, `sector_intelligence`, `earnings_calendar`, `concall_links`, `user_tickers`, `insights_cache`, `promoter_activity`, `promoter_activity_fetch_log`, `solo_analysis_cache`, `user_credits`, `api_partners`, `api_keys`, `api_key_products`, `api_usage` — confirmed by the exact `TABLES` array in `scripts/verify-migration.ts`, which is 15 of these 16, omitting only the legacy `user_connections`). Azure Blob Storage (container `transcripts`) holds the PDFs. **No vector database in production** — every query the app runs is exact-match/filter over Postgres rows or a blob-name substring search, never a similarity search. FAISS exists only in the archived prototype.
- **AI/LLM components**: exactly one provider (Gemini 2.5 Flash Lite) called directly via the Google SDK in `lib/pipeline.ts`, `lib/solo-pipeline.ts`, `lib/insights-pipeline.ts`, `lib/sector-narrative.ts` — each file re-implements its own `getGenAI()`/`invokeStructured()` helper rather than sharing one (see §B "Provider Abstraction: NOT PRESENT").
- **External integrations**: Gemini (`GOOGLE_API_KEY`), Azure Database for PostgreSQL (`POSTGRES_CONNECTION_STRING`), Azure Blob Storage (`AZURE_STORAGE_CONNECTION_STRING`, `AZURE_STORAGE_CONTAINER`), Microsoft Entra External ID (`AUTH_MICROSOFT_ENTRA_ID_ID/SECRET/ISSUER`), YouTube Data API v3 (`YOUTUBE_API_KEY`), Yahoo Finance (unofficial, no key), BSE/NSE public APIs (no key), Screener.in (scraped, no key). Legacy/unused env vars still present in `.env.local.example`: `NEXT_PUBLIC_SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` (Supabase repos are dead code), `GOOGLE_CLIENT_ID`/`SLACK_CLIENT_ID` (a Google/Slack OAuth flow referenced nowhere in the currently-wired auth path, which is Entra-only).
- **Configuration management**: plain `process.env.*` reads scattered per-file (`lib/pipeline.ts`'s `getGenAI()`, `lib/postgres/client.ts`'s `pgPool()`, `lib/repositories/storage.ts`'s `blobServiceClient()`) — no centralized config module or schema-validated env loader (e.g. no `zod`-parsed config object). Every consumer does its own `process.env.X!` non-null assertion.

## Part B — Architectural patterns: present vs. absent, with evidence

| Pattern | Verdict | Evidence |
|---|---|---|
| **Layered architecture** | **PRESENT** | Clean separation: `app/api/**` (interface) → `lib/pipeline*.ts` / `lib/services/*` (domain) → `lib/repositories/*` (data access) → `lib/postgres/client.ts` / Azure SDKs (infrastructure). `app/api/v1/analyze/route.ts` never touches `pg` or Gemini directly — it calls `runPipeline()` and `analysisRepo.saveAnalysis()`. |
| **Repository pattern** | **PRESENT, genuinely** | `lib/repositories/analysis.ts` defines an `AnalysisRepository` interface with 8 methods, and **two full independent implementations** (`SupabaseAnalysisRepository`, `PostgresAnalysisRepository`) that both satisfy it — real interface-based swappability, not just a class named "Repository" wrapping a single DB call. `lib/repositories/index.ts` is the single composition point deciding which implementation is live. This is confirmed further by `lib/repositories/storage.ts`'s `StorageRepository` interface with `SupabaseStorageRepository`/`AzureBlobStorageRepository` swap. |
| **Service layer** | **PRESENT, but thin** | `lib/services/sectorThesisService.ts`'s `SectorThesisService` takes repository interfaces as constructor-injected dependencies and composes multiple repository calls (`sectorRepo.getBySector` + `kpiRepo.getLatestByTickers` + `analysisRepo.listByTickersAndQuarterPair`) into one use-case result (`SectorThesisResult`). It is the **only** service in `lib/services/` — most of the app's "business logic" instead lives directly in `lib/pipeline*.ts` or inline in route handlers, so this is a real but narrow instance of the pattern, not an app-wide layer. |
| **Dependency injection** | **PARTIAL — manual constructor injection in one place, singleton imports everywhere else** | `SectorThesisService`'s constructor takes `{ sectorRepo, kpiRepo, analysisRepo }` as an explicit dependency object (`lib/services/sectorThesisService.ts:37-43`), and `lib/services/index.ts` wires the concrete singletons in at composition time — genuine DI, no container. Everywhere else (every pipeline file, every route handler), `analysisRepo`/`storageRepo`/etc. are imported directly as module-level singletons from `lib/repositories`. There is no DI container (no `tsyringe`/`inversify` in `package.json`). |
| **Factory pattern** | **NOT PRESENT** as a named pattern, but lazy-singleton factory functions exist: `pgPool()` (`lib/postgres/client.ts`), `supabaseAdmin()` (`lib/supabase/admin.ts`), `blobServiceClient()` (`lib/repositories/storage.ts`), `getGenAI()` (repeated per pipeline file) all lazily construct-and-cache a client on first call. This is the standard "lazy singleton" idiom, not a Factory in the GoF sense (no product-family selection at runtime). |
| **Strategy pattern** | **NOT PRESENT** | No place in the codebase selects between interchangeable algorithms at runtime via a common interface beyond the repository swap (which is a build-time/composition-time choice, not a per-request strategy selection). |
| **Adapter pattern** | **PRESENT, implicitly** | `SupabaseStorageRepository`/`AzureBlobStorageRepository` and `SupabaseAnalysisRepository`/`PostgresAnalysisRepository` each adapt a vendor-specific SDK (`@supabase/supabase-js`, `@azure/storage-blob`, `pg`) to one common domain interface — textbook adapter usage, arrived at as a byproduct of the repository pattern rather than a separately-named "Adapter" class. |
| **Facade pattern** | **PRESENT** | `runPipeline()`, `runSoloPipeline()`, `runInsightsPipeline()` are facades over the entire multi-call Gemini orchestration — callers (route handlers) invoke one function and get one payload back, with all fan-out/fan-in, caching, and validation hidden inside. |
| **DTO / schema pattern** | **PRESENT, at the public-API boundary specifically** | `lib/api-contracts/v1/company.ts`'s `CompanyResponseV1` interface + `toCompanyResponseV1()` mapper is a real anti-corruption layer: it translates the internal `Analysis` entity (itself already translated once from the pipeline's `DashboardPayload` via `lib/repositories/analysis.ts`'s `toEntity`/`fromEntity`) into a deliberately smaller, camelCase, externally-stable shape. Internally, `app/api/v1/**` routes mostly pass the pipeline's own `DashboardPayload`/`SoloPayload`/`InsightsPayload` straight through — no DTO layer between the internal pipelines and the first-party frontend, by design (`lib/repositories/analysis.ts`'s own comment explains `toDashboardPayload()`/`fromDashboardPayload()` exist specifically to preserve "the exact existing frontend contract"). |
| **Domain models** | **PARTIAL** | Each repository defines a domain entity distinct from its wire/JSONB shape (`Analysis` vs. `StoredPayload` in `analysis.ts`; `SoloAnalysis` vs. `SoloWirePayload` in `soloAnalysis.ts`) with explicit `toEntity`/`fromEntity` mapping functions — real domain-modeling discipline at the repository boundary. But the pipelines themselves (`lib/pipeline.ts`) operate directly on wire-shaped `DashboardPayload`/`SectionalInsight` types with no separate domain layer above the repository — the "domain model" is really the persisted JSONB payload shape, name notwithstanding. |
| **Provider abstraction (LLM)** | **NOT PRESENT** | Every pipeline file (`pipeline.ts`, `solo-pipeline.ts`, `insights-pipeline.ts`, `sector-narrative.ts`) independently defines its own `getGenAI()` and calls `@google/generative-ai`'s `GoogleGenerativeAI`/`getGenerativeModel` directly — there is no `LLMProvider` interface, no adapter that would let a different model vendor be swapped in without touching every pipeline file. Confirmed absent: no `lib/llm/` or `lib/providers/` directory, no interface with an `OpenAIProvider`/`AnthropicProvider`/`GeminiProvider` implementation set (contrast with the very real `AnalysisRepository`/`StorageRepository` provider abstraction one layer below). If asked "how would you swap Gemini for Claude," the honest answer is "edit `getGenAI()` and every `generationConfig` block in 4 files," not "change one config value." |
| **Configuration abstraction** | **NOT PRESENT** | No schema-validated config module (no `zod`/`envalid` parse-on-boot). Every file does its own `process.env.X!` read with a non-null assertion at the point of use; a missing env var fails at first *use*, not at boot. |
| **API versioning** | **NAMESPACE, not real versioning** | Both `app/api/v1/**` and `app/api/public/v1/**` hardcode `v1` in the path, and `lib/api-contracts/v1/*.ts` hardcodes `V1` in every exported type/function name (`CompanyResponseV1`, `toCompanyResponseV1`). There is no `v2`, no version-negotiation mechanism, and no code path that behaves differently by version — `v1` is a placeholder for a versioning scheme that would matter once a `v2` actually ships, not an active versioning system today. |
| **Event-driven architecture** | **NOT PRESENT** | No message queue, no pub/sub, no event bus, no webhook *emission* (the app receives no async callbacks either — even `/api/v1/request`'s transcript fetch is a synchronous request/response, capped at `maxDuration = 60`). Everything is direct function calls or synchronous HTTP request/response. |
| **Async processing / background jobs** | **NOT PRESENT as a job queue** | There is no worker process, no cron, no queue (`bull`/`bullmq`/similar absent from `package.json`). What looks like "background work" is really: (a) long-running synchronous route handlers up to Next.js's `maxDuration` (`300` for `/analyze`, `120` implied for `/analyze/solo`, `60` for `/request`), streamed to the client via NDJSON rather than run detached; (b) one genuinely fire-and-forget write — `runInsightsPipeline()`'s cache save (`setCachedInsights(...).catch(...)`, `lib/insights-pipeline.ts:432-434`) is explicitly non-blocking so a cache-write failure doesn't fail the user-facing response, but this is a single uncaught promise, not a job system. |
| **Streaming (NDJSON)** | **PRESENT, precisely traceable** | `app/api/v1/analyze/route.ts` constructs a `new ReadableStream({ async start(controller) {...} })`; a `send(data)` closure does `controller.enqueue(encoder.encode(JSON.stringify(data) + "\n"))`, guarded by a module-local `closed` flag (set on `controller.enqueue` throwing, i.e. a client disconnect) so no enqueue is attempted after close; a `setTimeout(..., 270_000)` fires an `{type:"error"}` event and closes the stream 30s before Vercel/Container-App-level `maxDuration` (`300`) would kill the function silently. The client side (`lib/api.ts`) reads via `response.body.getReader()`, buffers on `\n`, and dispatches each parsed line to an `onEvent` callback — `AgentPanel.tsx` renders directly off this event stream. Both the pipeline-level `ProgressEvent` unions (`lib/pipeline.ts:15-20`, `lib/solo-pipeline.ts:28-33`, `lib/insights-pipeline.ts:18-23`) and the wire NDJSON envelope share the same event vocabulary, so what the UI shows is a direct projection of pipeline execution state, not a simulated progress bar. |
| **Caching** | **PRESENT — real app-level caching, not just persistence** | Every cache table has explicit key, TTL, and invalidation semantics distinct from "a row exists": `analysis_results`/`solo_analysis_cache` — permanent until an explicit `force`/"Clear cache & re-analyze" bypass; `insights_cache` — 30-day app-enforced TTL checked in code (`CACHE_TTL_DAYS` in `lib/insights-pipeline.ts:253`, enforced inside `insightsRepo.getCached(ticker, qKey, CACHE_TTL_DAYS)`); `promoter_activity` — 24h fetch-log TTL in a **separate** `promoter_activity_fetch_log` table from the data itself; `concall_links` — permanent, bypassed only by an explicit `?retry=true` query param. `analysis_results.saveAnalysis()` does an explicit delete-then-insert per key (not a natural-key upsert), which is itself a form of cache-invalidation-by-replacement. The `supabaseAdmin()` client is also patched to force `cache: "no-store"` on every underlying `fetch()` (`lib/supabase/admin.ts:18-19`) specifically to defeat Next.js 14's *own* automatic fetch-response caching — documented in `TECHNICAL_ARCHITECTURE.md`'s "Why cache: no-store" section as having been root-caused from a real production bug (sector intelligence showing 15/17 sectors despite all 17 being inserted). |
| **State management (frontend)** | **PRESENT, deliberately minimal** | Plain React `useState`/`useEffect`/`useRef`/`useMemo` per `TECHNICAL_ARCHITECTURE.md §8` — no Redux/Zustand/Context-based global store (absent from `package.json`). `localStorage` (key `quantalyze_watchlist`) is the only cross-component shared client state, chosen explicitly for zero-latency page loads over a DB round-trip. |
| **Persistence boundaries** | **PRESENT, clean** | No route handler or pipeline file issues raw SQL or Supabase-client calls directly — every DB/storage access goes through a `lib/repositories/*.ts` class. The one exception worth naming: `scripts/*.ts` (migration tooling) talks to `pg`/Azure Blob directly, but those are explicitly one-shot operational scripts, not app runtime code. |
| **Feature flags** | **NOT PRESENT** | No flag service, no `NEXT_PUBLIC_FEATURE_*` pattern, no `.env`-driven boolean toggling behavior at runtime (grepped for "feature flag"/"LaunchDarkly" — no hits). The closest analogue is the `?retry=true` cache-bypass query param on `/api/v1/concall`, which is a manual cache override, not a feature flag. |
| **Testing infrastructure** | **NOT PRESENT** | No `*.test.ts`/`*.spec.ts` files anywhere in `app/`/`lib/`, no `jest.config.*`/`vitest.config.*`, no test runner in `package.json`'s `devDependencies` or `scripts`. If a reviewer asks "how is `computeMarketAlignment()`'s threshold logic verified," the honest answer is: it isn't, automatically — correctness relies on manual QA and the inline validation logic (`localValidation()`) that runs at pipeline time, not on unit tests. |
| **Observability / evaluation** | **PARTIAL — structured request logging, no metrics/tracing/eval framework** | `middleware.ts` emits one structured JSON log line per public-API request (`requestId`, `partnerId`, `keyId`, `endpoint`, `product`, `status`, `latencyMs` — `middleware.ts:80-93`) — genuine structured logging with a request-scoped correlation ID. Pipeline files log liberally via `console.log`/`console.error` with bracketed prefixes (`[Pipeline]`, `[Insights]`, `[request]`) for manual log-reading, not structured/queryable telemetry. **Absent**: no APM/tracing SDK (no OpenTelemetry, no Sentry, no Datadog in `package.json`), no LLM-output evaluation harness (no golden-set regression tests on prompt/schema changes), no metrics endpoint beyond `app/api/health/route.ts`'s presumed liveness check. |
| **Deployment/infra** | **PRESENT, and it's the headline architectural fact of this codebase** | `Dockerfile` — 3-stage build (`deps`→`builder`→`runner`), `npm run build` producing Next.js `standalone` output, runs as non-root `nextjs` user, `CMD ["node", "server.js"]`. `.github/workflows/deploy-azure.yml` — GitHub Actions, OIDC federation to Azure (`azure/login@v2`, no stored cloud credentials), `az acr login` + `docker build`/`push` to `quantalyzeacr.azurecr.io`, then `az containerapp update --name quantalyze-app-ca --resource-group quantalyze-prod-rg` on every push to `main`. This directly contradicts `TECHNICAL_ARCHITECTURE.md §9`'s Vercel cost model (serverless functions, 300s max duration, GB-hours pricing) — the *code* still carries Vercel-era artifacts (`export const maxDuration = 300` in `app/api/v1/analyze/route.ts`, a `vercel.json` with just `{"framework":"nextjs"}`, `@vercel/functions` in `package.json` dependencies) that are vestigial on Container Apps, where there is no serverless function timeout to respect — the 270s-inside-300s pipeline-timeout defense (`PIPELINE_TIMEOUT_MS` in the same route file) was designed around Vercel's silent-kill behavior and is now solving a problem that may no longer exist on a long-running container, though it remains harmless defensive code either way. |

## Part C — Documentation-drift summary (for interview framing)

This codebase is a strong, realistic example of what "the docs are the last thing updated" looks like in a fast-moving startup:

1. **Stack**: README/TECHNICAL_ARCHITECTURE describe Supabase (DB+Storage+Auth) + Vercel; the wired code is Azure Postgres + Azure Blob + Microsoft Entra External ID + Azure Container Apps. Primary-source proof: `docs/superpowers/plans/2026-07-09-repositories-and-migration.md`, `2026-07-10-azure-data-storage-migration.md`, `2026-07-10-azure-hosting-migration.md`, `2026-07-13-azure-auth-migration.md`, plus the full `scripts/*.ts` migration toolkit and `scripts/verify-migration.ts`'s literal table-by-table row-count/hash diff.
2. **Table count**: docs say "10 tables"; the actual migrated set (per `scripts/verify-migration.ts`'s `TABLES` array, plus the untouched `user_connections`) is 16.
3. **Agent count**: `lib/pipeline.ts`'s own header comment says "4 thematic agents"; the code (`AGENT_PROMPTS`) has held 5 since before this snapshot, and internal `console.log`s still hardcode `/4`.
4. **Credit quota**: `lib/credits.ts`'s header comment says "Default monthly quota = 600 ($6)"; the constant is `DEFAULT_QUOTA = 2_500`.
5. **A live, self-documented bug**: `lib/divergence-score.ts` reads fields off `insights_cache` that `lib/insights-pipeline.ts` never writes, and says so in its own comments, invoking "Strangler Fig discipline" as the reason it wasn't silently patched.

None of this should read as sloppiness — it reads as a team mid-migration, prioritizing shipping the infrastructure move and leaving a paper trail (`docs/superpowers/`) of *why*, while the user-facing README lagged behind by about a month. That is itself a legitimate, common, and worth-discussing engineering-management reality for a case study.

# Quantalyze — AI Evaluation

*Evidence-based read of what exists to evaluate the quality of AI (Gemini) output across the codebase — live and archived. All claims cite exact files/functions. Labels: IMPLEMENTED / PARTIALLY IMPLEMENTED / IMPLIED-ARCHITECTURALLY-PREPARED / NOT IMPLEMENTED / IMPLEMENTED-BUT-ARCHIVED.*

---

## 0. The one-sentence verdict

The **live product** (`app/`, `lib/`) has **zero automated quality evaluation of Gemini's output**. What it has is JSON-shape enforcement (Gemini's own `responseSchema` contract) plus one small piece of deterministic internal-consistency arithmetic. It has **no** golden datasets, **no** regression suite, **no** LLM-as-judge, **no** human review workflow, **no** drift/hallucination monitoring, **no** A/B testing. A real, working four-stage **LLM-as-judge evaluation framework** exists, fully coded and documented — but it lives in the **archived prototype** (`finance-agent/disclosure_pipeline/`), is invoked only via an opt-in CLI flag on a pipeline that is not wired into the live app, and there is no evidence it has ever produced a saved report in this repo (no `output/evaluation_report.*` artifacts present anywhere in the tree). Separately, a small number of TypeScript unit-test-*shaped* scripts in `finance-agent/scripts/` are not unit tests — they are manual smoke scripts (see `13_TESTING.md`), and none of them constitute AI evaluation in any rigorous sense (score thresholds, ground truth, statistical confidence). **These are categorically different things — "the code runs without throwing" is not "the AI's answer is correct" — and the live Quantalyze product only has evidence of the former.**

## 1. What exists — archived: `judge_evaluator.py` + `evaluation_report.py`

**Location**: `finance-agent/disclosure_pipeline/src/judge_evaluator.py` (527 lines) and `finance-agent/disclosure_pipeline/src/evaluation_report.py` (290 lines). Labeled **IMPLEMENTED-BUT-ARCHIVED** — this code runs, is well-structured, and does real LLM-as-judge evaluation, but it belongs to the "disclosure pipeline" prototype (part of the earlier "NotionWealth Intelligence" iteration, `README_ARCHIVE.md`), a completely separate codebase from the live Next.js app that only touched 15 commits total (`finance-agent/` in aggregate) against 159/89 for `app/`/`lib/`. It has never been ported into `lib/pipeline.ts`, `lib/insights-pipeline.ts`, or any other live pipeline.

### 1.1 The judge model and invocation pattern

`create_judge_llm()` (`judge_evaluator.py:32-43`) instantiates `ChatGoogleGenerativeAI(model="gemini-2.0-flash", temperature=0.0, ...)` — **the same model family** (Gemini) that generated the content being judged, at `temperature=0.0` explicitly "for consistent evaluation" (a comment on line 40). This is the classic same-family LLM-as-judge pattern, with the standard caveat this repo does not itself address: a same-family judge shares blind spots and systematic biases with the generator, so a score of "92% quality" from this judge says less about ground-truth correctness than a judge built on a different model family or grounded against human-labeled examples would.

### 1.2 What it scores — four discrete stages, each a separate judge prompt

| Stage | Function | What's evaluated | Prompt file:line | Output fields |
|---|---|---|---|---|
| 1. Semantic Extraction Quality | `validate_extraction()` | Whether text pulled from a disclosure PDF section (MD&A / Risk Factors / Accounting) is relevant, complete, and clean | `EXTRACTION_JUDGE_PROMPT`, `judge_evaluator.py:50-70` | `quality_score` (0-100), `is_relevant`, `has_meaningful_content`, `issues[]`, `reasoning` |
| 2. Change Detection Validity | `validate_change()` | Whether a detected QoQ change's old/new quotes actually appear in source text, are comparable concepts, and the description is accurate | `CHANGE_JUDGE_PROMPT`, `judge_evaluator.py:130-159` | `quote_accuracy_score`, `comparability_score`, `description_accuracy_score`, `overall_validity` (all 0-100), `issues[]`, `reasoning` |
| 3. Signal Classification Correctness | `validate_signal()` | Whether the assigned Positive/Negative/Noise label fits the change's actual content, against explicit signal definitions embedded in the prompt | `SIGNAL_JUDGE_PROMPT`, `judge_evaluator.py:222-245` | `signal_correctness_score`, `is_correct_signal` (bool), `suggested_signal`, `reasoning` |
| 4. Verdict Quality | `validate_verdict()` | Whether the final synthesized verdict is coherent with the underlying changes, has meaningful insights, and whether its final signal matches the pattern of changes | `VERDICT_JUDGE_PROMPT`, `judge_evaluator.py:298-322` | `coherence_score`, `insight_quality_score`, `signal_alignment_score`, `overall_verdict_quality`, `issues[]`, `reasoning` |

This is a genuinely well-designed evaluation taxonomy for a pipeline that goes PDF → extracted section → detected change → classified signal → synthesized verdict: **each stage's judge validates that specific stage's transformation**, not just the final output — meaning a bad verdict can be traced back to a bad extraction, a bad change-quote match, or a bad signal label, rather than a single opaque "is this good?" score. This is the right shape for a real evaluation framework and is worth reusing (see §4).

### 1.3 Orchestration — `run_full_evaluation()` (`judge_evaluator.py:387-527`)

Runs all four stages **in parallel** via `ThreadPoolExecutor(max_workers=8)` (`judge_evaluator.py:421`) — every extraction, every detected change, every signal, and the one verdict are all submitted as futures up front (`futures[future] = (task_type, key)`, lines 419-458) and collected via `as_completed()`. Failures are caught per-future (`except Exception as e: logger.warning(...)`, line 496-497) so one judge call failing doesn't abort the whole evaluation run. Response parsing is fragile-but-defensive: each `validate_*` function extracts JSON from the judge's raw text response with a regex (`re.search(r"\{.*\}", content, re.DOTALL)`, e.g. line 111), and **on parse failure, falls back to a hardcoded neutral score of 70** (e.g. `judge_evaluator.py:208-215`) rather than failing the evaluation — meaning a judge that returns malformed JSON silently produces a "70% — inconclusive" result indistinguishable in the aggregate summary score from a genuine 70% judged score. This is a real weakness: a systematic judge-parsing failure (e.g. the judge model changes its response format) would silently degrade every score toward 70 rather than surfacing as a hard failure.

Summary scores (`judge_evaluator.py:500-514`) average each stage's individual scores and combine into `overall_accuracy` — a single number meant to represent pipeline health across all four stages.

### 1.4 Reporting — `evaluation_report.py`

`generate_evaluation_report()` (`evaluation_report.py:19-47`) writes three things: `evaluation_report.json` (raw structured data), `evaluation_report.md` (human-readable, with per-company/quarter/section score tables, a "Flagged Changes (Score < 70%)" section listing the worst-scoring detected changes with their judge reasoning, and a status-emoji-driven recommendations block that switches text based on the `overall_accuracy` bucket — ≥85 "Excellent", ≥70 "Good", ≥50 "Needs Improvement", else "Poor", `evaluation_report.py:57-68`), and a color-coded terminal summary (`_print_terminal_summary()`, lines 239-291, using raw ANSI codes). This is a legitimate reporting pattern — the markdown report specifically surfaces the worst individual cases (flagged changes, incorrect signals) rather than only the aggregate, which is what an engineer actually needs to act on.

### 1.5 How it's invoked — and why that matters

`run_full_evaluation`/`generate_evaluation_report` are called from exactly one place: `finance-agent/disclosure_pipeline/src/pipeline.py:282-292`, inside a conditional block gated by `if run_evaluation and not dry_run and changes:` (`pipeline.py:275`). `run_evaluation` traces back to an **opt-in CLI flag**, `--evaluate` (`argparse` block near `pipeline.py:340-346`, wired through to `run_pipeline(..., run_evaluation=args.evaluate)`). This means:

- Evaluation is **not automatic** — a human has to remember to pass `--evaluate` when running the disclosure pipeline manually.
- There is **no CI hook, no scheduled job, no trigger tied to code changes** that runs this evaluation — it is a manual, opt-in CLI invocation of an archived prototype.
- A repo-wide search for `evaluation_report.json`/`evaluation_report.md` output files (the artifacts this code produces) finds none present anywhere in the tree — there's no evidence this was ever run and its output committed/retained, only that the code to do so exists and is coherent.
- **NOT IMPLEMENTED**: nothing resembling this exists for the live product's pipelines (`lib/pipeline.ts`, `lib/insights-pipeline.ts`, `lib/solo-pipeline.ts`, `lib/kpi-extractor.ts`, `lib/sector-narrative.ts`) — no judge model is ever invoked against their Gemini output anywhere in `app/` or `lib/`.

## 2. What exists — live product: precisely what's there, and precisely what isn't

### 2.1 IMPLEMENTED: JSON-shape enforcement via Gemini `responseSchema`

Every Gemini call site in the live app follows the same pattern — `lib/pipeline.ts:191-214` (`invokeStructured<T>`), `lib/insights-pipeline.ts:83-99`, `lib/solo-pipeline.ts` (~172-184), `lib/kpi-extractor.ts:368-385`, `lib/sector-narrative.ts:118-183`. Each constructs a `GoogleGenerativeAI` client, calls `getGenerativeModel({ ..., generationConfig: { responseMimeType: "application/json", responseSchema: <SCHEMA>, temperature: 0 } })`, and does `JSON.parse(result.response.text()) as T`. The `<SCHEMA>` objects (e.g. `QUARTER_SNAPSHOT_SCHEMA`, `SECTIONAL_INSIGHT_SCHEMA`, `SECTOR_KPI_SCHEMA`, `NARRATIVE_SCHEMA`, `SOLO_SCHEMA` — all built from `SchemaType.OBJECT` trees, e.g. `lib/pipeline.ts:81-162`) are Gemini's own structured-output contract: the model is constrained server-side (by Google) to emit JSON matching the declared shape (field names, types, enum values where specified).

**This is real and matters** — it eliminates an entire class of failure (missing fields, wrong types, unparseable free text) that plagues naive prompt-and-hope LLM integrations. But it is a **shape** guarantee, not a **content** guarantee: `responseSchema` cannot verify that a number is factually correct, that a quoted figure actually appears in the source transcript, that a signal classification (`Positive`/`Negative`/`Noise`) matches the substance of what was said, or that the model didn't hallucinate a metric that isn't in the transcript at all. There is **no zod, no manual field-by-field content validation, no range/plausibility check** anywhere in the live pipelines — confirmed by a repo-wide search: `zod` does not appear as a dependency in `package.json`, and grepping `app/` and `lib/` for `\bzod\b` returns zero matches. The `.min(`/`.max(` matches that do appear (e.g. `app/api/v1/screener/route.ts`) are plain JS array/string method calls, not schema-validation library usage.

### 2.2 PARTIALLY IMPLEMENTED: deterministic internal-consistency check — `localValidation()`

`lib/pipeline.ts:631-658`. After the Gemini insight-generation agents run, this function walks every `metric` inside every `insight` and flags a **sign-consistency violation**: if `signal_classification === "Positive"` but `signal_score < 0`, or `signal_classification === "Negative"` but `signal_score > 0`, it sets `validation_status = "flagged"` and a human-readable `validation_note` (e.g. `"Signal is Positive but score is -3.2"`, line 643). It then computes `validationScore = ((total - flagged) / total) * 100` (line 652) — a single percentage representing "what fraction of extracted metrics are internally self-consistent." This is **real**, runs on every Delta Analysis (`lib/pipeline.ts:841`, `const { insights: validatedInsights, validationScore, flaggedCount } = localValidation(rawInsights)`), and its output (`validationScore`, `flaggedCount`) feeds into `computeConfidence()` in `app/api/v1/screener/route.ts:76-106` as one input among several rule-based confidence-adjustment factors.

But it is important to be precise about what this is **not**: it is a pure arithmetic self-consistency check (does the sign of a number match a label the same model assigned), not a correctness check against the source transcript or against any ground truth. A model that is confidently, consistently wrong about a number passes this check with a perfect 100% validation score — `localValidation` cannot detect hallucination, only internal contradiction. It never calls an LLM (confirmed: no `generateContent`/judge invocation anywhere in the function), and there is no retry, no re-prompt, and no rejection of a Gemini response even when every metric is flagged — flagged metrics are still shown to the user with a note attached, not filtered out or regenerated.

### 2.3 NOT IMPLEMENTED / rule-based, not AI-evaluative: `confidence_pct` in the screener

`computeConfidence()` (`app/api/v1/screener/route.ts:76-` onward) is worth naming precisely because "confidence score" is exactly the kind of term that gets conflated with AI evaluation. It is **not** a model-reported confidence, a judge score, or a calibrated probability of correctness. It's a deterministic penalty ladder over several *already-computed, non-LLM* signals: `validationScore`/`flaggedCount` from §2.2 (mapped to an `earningsQuality` factor, `0.5 + validationScore/200`, line 86), a flat `-12%` penalty per one-time-item flag (line 92, floored at 0.5), a management-evasiveness-derived factor (line 98), and a `disclosureInflation` flag that multiplies confidence by `0.4` if set (line 104). This is legitimate, useful rule-based product design — a genuinely good idea for surfacing *why* a signal might be unreliable to an analyst — but it should never be described in an interview as "the system evaluates AI output"; it evaluates a handful of derived heuristics, none of which check factual accuracy against the transcript.

## 3. Why "unit tests that assert on LLM output" and "AI evaluation" are different things — stated explicitly, per the task's requirement

There are no unit tests asserting on LLM output shape or content anywhere in this repo — see `13_TESTING.md` for the full test inventory (no JS test framework is even installed: `jest`/`vitest`/`playwright`/`@testing-library/*` are all absent from `package.json`'s `devDependencies`). But even hypothetically, it's worth stating the distinction plainly because it's the crux of what's missing:

- A **unit test** on LLM output asserts a fixed, deterministic property that must hold on every run — e.g. "the response is valid JSON," "the `overall_signal` field is one of the four allowed enum values," "`saveAnalysis` was called with the right ticker." These are testable because the property being checked doesn't itself require judgment — Gemini's `responseSchema` already guarantees the JSON-shape property server-side (§2.1), so a unit test re-asserting it would be redundant; a unit test on the *content* correctness of `analysis.summary` (is this actually a good summary of what management said?) is not something a unit test's pass/fail boolean can meaningfully express.
- **AI evaluation** asks a fundamentally different, graded question — is this output *good*, where "good" means faithful to the source, factually accurate, appropriately classified, and useful — against either a human-labeled ground truth (a golden dataset) or a calibrated judge model, producing a *score* (a distribution, a percentage, a pass rate over N examples) rather than a binary pass/fail on one deterministic property.

Quantalyze's live product has **none of the second category** for its Gemini output, and — per the instructions for this file — that is stated here plainly rather than allowed to be implied by the presence of `responseSchema` and `localValidation`, which, while real and useful, are shape/internal-consistency checks, not evaluation.

## 4. A concrete, Quantalyze-specific evaluation framework proposal

Generic "add an eval framework" advice is not useful here — this is what one would look like **for this specific pipeline**, reusing what already exists in the repo (both live and archived) rather than proposing something foreign to the codebase's own patterns.

### 4.1 Seed a golden set from transcripts already in the repo

`finance-agent/multiagent_analysis/all-pdfs/` contains 10 real earnings-call transcript PDFs for Indian NSE-listed companies — `ICICI_Q1_2026.pdf`, `Bajaj_Q1_2026.pdf`, `SBI_Q4_2025.pdf`, `Bharti_Q2_2026.pdf`, `Bharti_Q3_2026.pdf`, `Bajaj_Q2_2026.pdf`, `HDFC_Q2_2026.pdf`, `SBI_Q3_2025.pdf`, `ICICI_Q4_2025.pdf`, `HDFC_Q3_2026.pdf` — following exactly the `{TICKER}_{Quarter}.pdf` naming convention `lib/pipeline.ts:224`'s `resolvePdfKey()` already expects for the live pipeline's own transcript storage keys. This is a directly reusable, zero-cost starting golden set: five of these already form two adjacent-quarter pairs per ticker (`Bajaj_Q1_2026`/`Bajaj_Q2_2026`, `HDFC_Q2_2026`/`HDFC_Q3_2026`, `Bharti_Q2_2026`/`Bharti_Q3_2026`, `SBI_Q3_2025`/`SBI_Q4_2025`, `ICICI_Q4_2025`/`ICICI_Q1_2026`) — exactly the QoQ input shape `POST /api/v1/analyze` (`app/api/v1/analyze/route.ts`) requires. Upload these into the live app's `transcripts` Azure Blob container (via `storageRepo.upload()`, `lib/repositories/storage.ts`), run Delta Analysis on each pair once with a human analyst reviewing the output, and hand-correct/annotate the resulting `DashboardPayload` (expected `overall_signal`, expected key metrics with source page/quote references, expected earnings-delta bullets) — that becomes the first golden set of expected-output pairs, in the same `{ticker, q_prev, q_curr} → expected DashboardPayload` shape the live pipeline already produces and persists (`lib/repositories/analysis.ts`).

### 4.2 A regression suite that re-runs cached transcripts and diffs structured output

Because the live pipeline already caches every result keyed by `(ticker, q_prev, q_curr)` in `analysis_results` (`lib/repositories/analysis.ts`, `getCachedAnalysis`/`saveAnalysis`), a regression suite is cheap to build without new infrastructure: a script (in the `scripts/` convention already used for `scripts/migrate-postgres-data.ts` etc.) that, for each golden-set entry, calls `runPipeline()` directly (bypassing the HTTP route, same as `app/api/v1/analyze/route.ts` does internally) with `force: true`, and diffs the new `DashboardPayload` against the golden-set's saved expected payload field-by-field: exact match required on `overall_signal` (it's a closed four-value enum — `Positive`/`Negative`/`Mixed`/`Noise` — so exact match is a meaningful, cheap check, unlike free text), numeric tolerance (e.g. ±0.5) on `overall_score` and each metric's `signal_score`, and a semantic-similarity or judge-scored check (not exact string match — Gemini's free-text bullets will legitimately vary run-to-run at `temperature: 0` only up to floating-point/decoding nondeterminism) on `earningsDelta` bullet text. Run this as a scheduled GitHub Actions job (there is currently no CI test step at all — see `14_DEVOPS_CLOUD.md`) against the fixed golden set whenever `lib/pipeline.ts`'s prompts change, catching prompt-edit regressions before they reach production — the single most valuable and cheapest-to-build piece of this proposal, because it requires zero new judge-model spend for the exact-match fields.

### 4.3 LLM-as-judge, directly adapting `judge_evaluator.py`'s stage taxonomy

The archived judge (§1) already has the right shape for this pipeline's own stages — it just needs porting from the disclosure-pipeline's stage names to Quantalyze's actual pipeline stages, and from LangChain/`ChatGoogleGenerativeAI` to the `@google/generative-ai` SDK already used everywhere in `lib/`:

| Archived judge stage | Quantalyze-specific equivalent | Live pipeline function it would validate |
|---|---|---|
| Semantic Extraction Quality | Quarter-snapshot extraction quality (is the per-domain snapshot actually grounded in the transcript, not hallucinated) | `runThematicAgent()` output against `QUARTER_SNAPSHOT_SCHEMA`, `lib/pipeline.ts` |
| Change Detection Validity (quote accuracy against source text) | Does each earnings-delta bullet's implied claim actually appear in the transcript text passed to `runTemporalDelta()`/`runEarningsDeltaAgent()`? | Directly reusable pattern — feed the judge the same `text_prev`/`text_curr` window already extracted by `extractPdfText()`, `lib/pipeline.ts:240` |
| Signal Classification Correctness | Does `signal_classification` match what was actually said, independent of `localValidation()`'s sign-only check | A genuine upgrade over §2.2 — catches a model that's internally consistent (sign matches label) but substantively wrong about the label |
| Verdict Quality | Coherence between `overall_signal`/`overall_score` (`computeOverallSignal()`, `lib/pipeline.ts:662-676`) and the individual per-metric signals feeding it | Reuses the same "does the aggregate match the parts" judge prompt pattern from `VERDICT_JUDGE_PROMPT` |

Ship this as an **opt-in flag on the existing pipeline** exactly as the archived version did (`--evaluate`/`run_evaluation`, §1.5) rather than a synchronous blocker on every user-facing request — Quantalyze's live analyze route already has a hard 300s `maxDuration` (`app/api/v1/analyze/route.ts:9`) and a 270s internal pipeline timeout (`PIPELINE_TIMEOUT_MS`, line 84); a judge pass adds real latency and Gemini spend that has no place in the synchronous request path. Instead, run it asynchronously against the golden set (§4.2's scheduled job) and, longer-term, as a sampled background job against a small percentage of real production analyses — writing scores into a new table (following the existing migration convention, `supabase/migrations/012_evaluation_scores.sql`) rather than the archived version's flat-file JSON/markdown reports, so scores are queryable over time per-ticker and per-pipeline-version.

### 4.4 Field-level validation against the declared schema — closing the gap in §2.1

Beyond Gemini's own `responseSchema` shape guarantee, add real content-plausibility checks Quantalyze can validate deterministically without a judge call: cross-check any extracted revenue/margin figure against the *previous quarter's already-cached* `analysis_results` row for the same ticker (a >50% QoQ swing in a metric like EBITDA margin is either real news or a hallucination — flag, don't block, exactly following `localValidation()`'s existing flag-don't-reject pattern) and re-run `resolvePdfKey()`'s own `%PDF` magic-byte check (already done for input, `lib/pipeline.ts:243-248`) as a lightweight sanity check that a "Quote_Old"/"Quote_New"-style extracted string literally appears as a substring in the source `extractPdfText()` output before ever showing it to a user — a much cheaper version of the archived judge's stage-2 quote-accuracy check that needs no LLM call at all.

### 4.5 Human evaluation workflow

None exists today (§2.4). The cheapest version worth building: a lightweight thumbs-up/down + optional note on each Delta Analysis result in `DashboardClient.tsx`, written to a new `analysis_feedback` table keyed the same way as `analysis_results` — this both surfaces real production error cases for free (no synthetic golden set can anticipate every real transcript's edge cases) and, over time, becomes a second, human-labeled golden set independent of and more trustworthy than the same-family LLM-judge approach in §4.3.

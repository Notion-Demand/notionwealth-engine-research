# Architecture Decision Log

Each entry reconstructs a real design decision from primary evidence in the
repository — commit-count disparities, README diffs, dated planning docs under
`docs/superpowers/`, and the actual code. Where the repository doesn't state a
rationale explicitly, the reasoning is marked **INFERRED** and the evidence for the
inference is given alongside it.

A note on sourcing: this repository has no `.git` directory in the extracted copy
used for this analysis, so exact commit counts/dates could not be independently
re-verified by running `git log`. The "15 commits vs. 159/89" figures and the "Jan
15 2026 initial commit" / "Feb 27 2026 pivot commit" facts are taken as given from
the task brief, which states them as established facts about the real repository
history; every other claim below is drawn directly from file contents that are
present and readable in this checkout (READMEs, dated planning docs, and code).

## 1. THE BIG ONE — From "NotionWealth Intelligence" (multi-agent/RAG/memory platform) to Quantalyze (lean Next.js + direct Gemini calls)

| | |
|---|---|
| **Decision** | Abandon the ambitious Python multi-agent decision-intelligence platform (`finance-agent/`, frozen since the Feb 27 2026 "move Next.js app to repo root" commit) as the product's core, in favor of a lean Next.js app calling Gemini directly with 3-5 parallel schema-constrained calls per feature, backed by a Postgres cache. |
| **Problem** | `README_ARCHIVE.md` states the original ambition plainly: "NotionWealth Intelligence... is not a chatbot. It is a multi-agent cognition layer" with ingestion agents, "multi-layer memory" (semantic/vector + structured + research-session memory), specialized research agents (financial/risk/competitive/portfolio), a control plane doing "task routing and orchestration... verification and evidence attachment," and a "Research Replay Engine" for auditable, replayable decision workflows. The directory structure it documents (`core/` — embeddings, vector memory; `agents/`; `control/`; `tools/` — an MCP tool layer; `ui/`; `mcp_server.py`) is a genuine attempt at an institutional-grade agentic research platform, not a demo. That ambition is real and still exists on disk: `finance-agent/` has `agents/`, `api/`, `cache/`, `control/`, `core/`, `db/`, `fetcher/`, `integrations/`, `multiagent_analysis/`, `scripts/`, `tools/`, `ui/` — the full shape the archive README describes. |
| **Chosen approach** | Everything the live product actually ships (`app/`, `lib/`, `components/`) is a from-scratch Next.js/TypeScript rewrite: no vector store, no persistent multi-layer memory, no control-plane task router, no replay engine, no MCP server, no Streamlit UI, no FastAPI backend serving the live product (`finance-agent/api/` still exists and even has Gmail/Slack integrations, but nothing in `app/`/`lib/` calls it — the Azure Auth Migration design doc's Non-Goals section is the one place it's referenced as still theoretically live: "Update the FastAPI backend's independent JWT verification... mandatory"). What replaced the control plane's orchestration is three flat, stateless pipeline functions (`lib/pipeline.ts`, `lib/solo-pipeline.ts`, `lib/insights-pipeline.ts`) — each a sequence of parallel Gemini calls with hard-coded prompts and JSON-schema-constrained output, no agent framework, no tool-calling, no dynamic routing. |
| **Alternative** | Continue building out the multi-agent platform: finish the vector-memory ingestion layer, wire the control plane's verification/replay engine into a real UI, and ship the Streamlit-based decision-intelligence interface `README_ARCHIVE.md` names as the "Product Layer." |
| **Why chosen** | INFERRED from the evidence trail, since no single document states "we chose lean over ambitious and here's why" — but the trail is unusually legible for an inference: (1) **Commit-count asymmetry.** 15 commits total ever touched `finance-agent/` against 159 for `app/` and 89 for `lib/` — a >10x investment ratio favoring the lean rewrite, and every one of those 15 commits necessarily predates the Feb 27 2026 pivot (the directory has been untouched since). (2) **The pivot commit's own message** — "move Next.js app to repo root" — describes a *structural promotion*: the Next.js app stops being a satellite/frontend-only piece next to the Python platform and becomes the whole repository's center of gravity, exactly the signature of a team deciding the rewrite is now the product. (3) **What actually shipped.** `README.md`'s entire feature list (Deep Dive, Delta, Promoter Pledge Monitor, Evasiveness Score, Multi-Quarter Insights, Screener, Calendar, Videos, Watchlist) is fully implemented in the Next.js app with real Supabase-then-Azure-backed persistence and a live production URL — the archived platform's feature list (institutional memory, replay, cross-portfolio reasoning, capital allocation modeling) has zero corresponding shipped surface anywhere in `app/`. A team building toward a real, sellable product chose the path that actually reached a customer over the path that was more architecturally ambitious. (4) **Cost/complexity mismatch for the actual customer.** The archived platform's "portfolio-level reasoning," "capital allocation modeling," and "cross-company reasoning" describe an institutional/hedge-fund-scale problem; the live product's actual customer (per `PRODUCT_NOTES.md`'s 2026-06-15 entry) is a PMS/family-office analyst who wants a fast, trustworthy per-company/per-quarter signal — a narrower, higher-frequency, lower-latency need that a "multi-agent cognition layer" with persistent memory and replay is arguably over-engineered for. |
| **Benefits** | Time-to-market (a working, revenue-generating product exists; the archived platform never shipped a UI beyond a `streamlit run` dev command). Operational simplicity — no vector DB to run/scale/pay for, no persistent-memory consistency model to reason about, no control-plane orchestration bugs to debug; a request is a stateless function call. Cost predictability — `TECHNICAL_ARCHITECTURE.md` §9 puts total Gemini cost at ~$1.00-1.50/user/month, a figure only possible because there's no embedding/retrieval overhead and no standing infrastructure beyond Postgres+Blob. Easier onboarding — a new engineer can read `lib/pipeline.ts` top to bottom in one sitting; understanding the archived platform requires understanding an entire agent framework's contracts first. |
| **Costs** | Real capability was left behind, not just complexity: no persistent research memory (every analysis is stateless and re-derived from the transcript each time — nothing "learns" across runs the way the archive's "institutional learning and audit trail" promised), no cross-company/portfolio-level reasoning (each ticker is analyzed independently; nothing in the live product can answer "how correlated is my portfolio's risk exposure"), no verification/replay engine (the live product's only verification is `lib/pipeline.ts`'s cheap local `signal_score`-vs-`signal_classification` consistency check — a much thinner guarantee than the archive's "verification is mandatory... traces are first-class artifacts" design philosophy). If Quantalyze's product ambitions ever grow toward the archive's original scope (true portfolio-level reasoning, persistent research sessions), that work starts largely from zero — the frozen `finance-agent/` code is nearly 7 months stale relative to the live app's data model and won't cleanly graft on. |
| **Future consequences** | The lean architecture is a good bet *as long as* the product's core loop stays "one company, one or a few quarters, one signal" — which is true today and is what's actually priced and sold (`lib/credits.ts`'s three metered actions). The moment a customer asks for genuine cross-portfolio reasoning or persistent multi-session research continuity (both explicitly named in `PRODUCT_NOTES.md`'s evaluated-but-deferred "Divergence Screener"/"Governance Score API" surfaces), the team will face a real rebuild-vs-retrofit decision — and the archived platform, however architecturally closer to that need, is stale enough (frozen mid-Feb, while `app/`/`lib/` have had 248 combined commits since) that it's more likely to be a design reference than reusable code. |

## 2. Repository pattern adoption (`lib/repositories/*.ts`)

| | |
|---|---|
| **Decision** | Introduce a formal Repository interface + implementation layer (12 interfaces, one composition root at `lib/repositories/index.ts`) wrapping every database/storage access. |
| **Problem** | Per `docs/superpowers/plans/2026-07-09-repositories-and-migration.md`: 31 files called `supabaseAdmin()` directly across 11 Postgres tables and one Storage bucket — every provider-specific detail (query-builder syntax, RLS assumptions, Supabase-specific error shapes) was smeared across the whole codebase. |
| **Chosen approach** | Per-domain files (`lib/repositories/analysis.ts`, `sectors.ts`, `kpis.ts`, etc.), each declaring a domain entity (camelCase, provider-agnostic), a repository `interface`, and a `SupabaseXRepository implements` class — migrated one domain at a time via the Strangler Fig pattern, live system running throughout, verified only by `npx tsc --noEmit` plus manual smoke checks (no test runner exists in this repo, stated explicitly in every migration plan's Testing section). |
| **Alternative** | Leave direct `supabaseAdmin()` calls in place and defer any abstraction until (or unless) a provider swap was actually decided. |
| **Why chosen** | Explicitly stated, not inferred: `docs/superpowers/specs/2026-07-09-data-wrapper-and-public-api-design.md`'s Context section says this is "prep work for the already-decided Supabase→Azure migration... introducing the abstraction now, while still safely on Supabase, so the eventual provider swap is contained to a handful of files instead of 31." The same spec is unusually explicit that this is deliberately more structure than the strict v1 feature set needs, "because the target is a multi-year platform... not a one-off script," and lists seven architectural principles (repositories persistence-only, services own orchestration, routes stay thin, provider SDKs never escape the repository layer, external contracts never expose internal models, infrastructure replaceable through composition roots) as the checklist for every future addition. |
| **Benefits** | The bet paid off in an unusually verifiable way: the actual Postgres cutover (`docs/superpowers/specs/2026-07-10-azure-data-storage-migration-design.md`) touched only the 11 repository implementation files, `lib/postgres/client.ts`, and the one-line composition-root swap in `lib/repositories/index.ts` — not one route handler changed. That's the exact ROI the pattern was purchased for, realized. |
| **Costs** | Real added indirection for a young, low-traffic product (every read/write now passes through an interface, a domain-entity mapping function, and a composition-root lookup, instead of one Supabase call). The dormant `SupabaseXRepository` classes doubled the maintenance surface of every repository file for the migration's safety-window duration — and, per this codebase's own tech-debt findings, considerably longer than that window (see `20_TECHNICAL_DEBT_AND_GAPS.md`). |
| **Future consequences** | The pattern is now proven twice over (Postgres cutover succeeded cleanly) and sets up a *third* clean swap opportunity if the AI provider itself is ever abstracted the same way (see ADR #3) — but only if that discipline is actually extended there, which it currently is not. |

## 3. Provider abstraction for the LLM — direct Gemini SDK calls, no abstraction layer

| | |
|---|---|
| **Decision** | Call `@google/generative-ai`'s `GoogleGenerativeAI` class directly from `lib/pipeline.ts`, `lib/solo-pipeline.ts`, `lib/insights-pipeline.ts`, `lib/sector-narrative.ts`, and `lib/kpi-extractor.ts` — no `LLMClient` interface, no provider-swap seam analogous to the repository layer's. |
| **Problem** | Every pipeline needs a schema-constrained JSON call to an LLM, with a per-call timeout and consistent error handling. |
| **Chosen approach** | A near-identical `getGenAI()` helper function, copy-pasted (not shared) into at least three files, each constructing its own `GoogleGenerativeAI` instance and its own `invokeStructured`-style timeout/parse wrapper. |
| **Alternative** | A `lib/llm/client.ts` module — one `getGenAI()`, one retry/timeout wrapper, one place to add a second provider or centralized cost/token logging — exactly mirroring the repository layer's composition-root discipline, but for the AI provider instead of the database provider. |
| **Why chosen** | INFERRED, and this is the one place this codebase's stated architectural principles (see ADR #2) were *not* extended to a second provider seam that plausibly deserved the same treatment. Plausible reasons: (a) at a single-model-family, single-provider product this early, the abstraction has no proven near-term payoff the way the DB abstraction did (there was an *already-decided* Azure migration driving that one; there is no announced or evidenced plan to swap Gemini for another model provider); (b) the archived `finance-agent/` prototype *did* target a different SDK generation (Vertex AI-style access per `README_ARCHIVE.md`'s "core/" ingestion-agent description), and the live rewrite may simply not have carried that abstraction-mindedness forward when the LLM-calling code was rewritten fresh for `@google/generative-ai`; (c) three call sites felt small enough that duplication was "cheaper" than an abstraction, without accounting for the compounding cost as a fourth and fifth pipeline (`lib/sector-narrative.ts`, `lib/kpi-extractor.ts`) were added following the same duplicated pattern. |
| **Benefits** | Zero indirection tax; each pipeline file is fully self-contained and readable without chasing a shared module; genuinely fast to build and easy to debug for any one pipeline in isolation. |
| **Costs** | Real, already-materialized duplication (5+ copies of essentially the same `getGenAI()`/timeout-wrapper logic); no single place to add retry-with-backoff, centralized cost/token telemetry, or a provider-swap seam if the model choice ever needs to change (e.g. Gemini pricing/availability shift, or a customer contract requiring a specific model). Bugs in the timeout/parsing logic (if any are found) must be fixed in every copy independently — a maintenance tax that grows with every new pipeline. |
| **Future consequences** | If the product ever needs a second model (a customer-specific fine-tune, a fallback provider for reliability, or a cheaper model for a lower-tier feature), this is now a multi-file refactor instead of a one-file composition-root swap — the exact problem the repository pattern was built specifically to avoid for the database layer, unaddressed here. |

## 4. Structured outputs via Gemini's JSON schema mode vs. free-text + manual parsing

| | |
|---|---|
| **Decision** | Every Gemini call in the live pipelines uses `responseMimeType: "application/json"` + an explicit `responseSchema` (Gemini's structured-output/JSON-mode feature) — never free-text generation followed by regex/manual JSON extraction. |
| **Problem** | LLM free-text output is unreliable to parse programmatically — malformed JSON, extra prose around a JSON blob, inconsistent field names/types across calls — and a financial-analysis product cannot silently corrupt or drop data because of a parsing failure. |
| **Chosen approach** | Every schema (`QUARTER_SNAPSHOT_SCHEMA`, `METRIC_DELTA_SCHEMA`, `SECTIONAL_INSIGHT_SCHEMA`, `EVASIVENESS_SCHEMA`, `BULLETS_SCHEMA`, `KEY_METRICS_SCHEMA` in `lib/pipeline.ts`, and their siblings in the other two pipeline files) is declared with Gemini's `SchemaType` enum (`OBJECT`, `ARRAY`, `STRING`, `NUMBER`, enum-constrained strings via `format: "enum"`), and every call site does `JSON.parse(result.response.text())` trusting the schema guarantee rather than defensively re-validating. |
| **Alternative** | Prompt-engineer a "respond only with JSON" instruction and hand-write parsing/validation with a fallback for malformed output (the more common pattern before native structured-output APIs matured). |
| **Why chosen** | Explicitly stated: `TECHNICAL_ARCHITECTURE.md` §10 lists this first among "Why Gemini 2.5 Flash Lite" — "Structured JSON output via `responseSchema` — guarantees valid JSON, no parsing failures." |
| **Benefits** | Eliminates an entire class of production bugs (malformed-JSON crashes, silently-wrong field names) that would otherwise be common at this call volume (~20 Gemini calls per Delta Analysis run). Enum-constrained fields (`signal_classification`, `ui_component_type`) get validated *by the model provider*, not by downstream code — a real reliability win specific to using a frontier model with native schema support. |
| **Costs** | Coupling to a provider feature — this exact mechanism (`SchemaType`, `responseSchema`) is Gemini-specific API surface; a provider swap (see ADR #3's future-consequences) would need to re-implement equivalent guarantees against whatever structured-output mechanism (or lack thereof) the new provider offers, which is not guaranteed to have equivalent reliability. The code still trusts `JSON.parse()` unconditionally after a schema-constrained call rather than defensively re-validating shape at runtime — reasonable given the provider's guarantee, but a single point of trust in an otherwise validation-heavy pipeline. |
| **Future consequences** | This decision is a strong argument *for* staying on Gemini (or another provider with equally robust structured output) rather than a cost/latency argument alone — switching providers isn't just an SDK-call change, it's potentially a reliability regression unless the new provider's structured-output guarantees are verified equally strong. |

## 5. Caching architecture — Postgres cache tables vs. a dedicated cache layer

| | |
|---|---|
| **Decision** | Cache every pipeline's output as a JSONB payload in a dedicated Postgres table per feature (`analysis_results`, `solo_analysis_cache`, `insights_cache`, `sector_intelligence`, `concall_links`, `kpi_snapshots`, `earnings_calendar`), keyed on the natural business key (ticker+quarter-pair, ticker+quarter, ticker+quarters-key, etc.) — no Redis, no in-memory cache, no CDN-level caching. |
| **Problem** | The pipelines are expensive (up to 20 Gemini calls, 15-270 seconds) and their inputs (a specific ticker's specific quarter-pair transcript comparison) are immutable once analyzed — re-running the same analysis for the same inputs is pure waste. |
| **Chosen approach** | The database that already holds every other piece of application state also holds the cache, as a plain table with a JSONB payload column and a natural-key lookup — `analysisRepo.getCachedAnalysis()` is a normal repository method, not a separate cache-client call. |
| **Alternative** | A dedicated cache layer (Redis/Memcached) with TTL-based eviction, separate from the system of record. |
| **Why chosen** | INFERRED, though strongly supported: (1) most of these caches are described as **permanent** in `TECHNICAL_ARCHITECTURE.md` §7 ("Permanent — Manual 'Clear cache & re-analyze'") — a financial analysis of Q3 FY26 vs Q4 FY26 for a given ticker does not go stale the way a typical web-cache entry does, since the underlying transcripts never change; a TTL-based cache is solving a problem this data mostly doesn't have. (2) Running a second stateful service (Redis) adds real operational surface (provisioning, monitoring, a second connection pool, a second failure mode) for a product whose actual cache-hit unit economics (`TECHNICAL_ARCHITECTURE.md` §9: ~$0.03 per Delta Analysis run) don't obviously justify sub-millisecond cache reads over Postgres's tens-of-milliseconds. (3) Postgres was already the system of record — reusing it for cache avoids a consistency problem (cache and DB disagreeing) that a separate cache layer would introduce for free. |
| **Benefits** | One fewer piece of infrastructure to run, monitor, and pay for. Cache entries get the same durability, backup, and (post-migration) VNet-private-networking guarantees as every other table, with zero extra engineering. Cache invalidation logic is just SQL (`DELETE ... WHERE ...` before insert, as seen in `lib/repositories/analysis.ts`), no separate cache-invalidation protocol to design. |
| **Costs** | No sub-millisecond cache reads (a real cost if traffic ever grows enough that Postgres read latency on hot cache keys becomes the bottleneck). No built-in TTL/eviction primitive — the app enforces its own rules in code (`insights_cache`'s "30 days (app-enforced)" per `TECHNICAL_ARCHITECTURE.md` §7 is application logic, not a database feature). All cache reads compete with transactional query load on the same connection pool/instance. |
| **Future consequences** | This is a good decision at current scale and will likely stay good as long as cache-read volume stays proportional to actual analysis-triggering volume (which is inherently rate-limited by the credit system, `lib/credits.ts`) rather than, say, becoming a high-QPS public API response cache — the moment cache reads dominate database load (plausible if the public API partner surface grows), a Redis-in-front-of-Postgres layer becomes the natural next step, not a full rearchitecture. |

## 6. Public API + credits system — turning the internal pipeline into a metered external product

| | |
|---|---|
| **Decision** | Build a separate, narrower public API surface (`app/api/public/v1/**`, guarded by `middleware.ts`) on top of the same repositories the internal app uses, with its own API-key/entitlement/rate-limit model (`lib/repositories/apiAccess.ts`) — entirely additive, the internal portal explicitly untouched. |
| **Problem** | Per `docs/superpowers/specs/2026-07-09-data-wrapper-and-public-api-design.md`'s Context: a need to expose "curated intelligence products without revealing prompts, pipeline internals, or source code" to enterprise partners (PMS firms first, AMCs second), explicitly **not** self-serve — "API keys are manually provisioned per partner — no signup flow, no self-serve billing in this version." |
| **Chosen approach** | A two-layer API structure (a stable resource layer, `data:companies`/`data:sectors`, plus a productized view on top, `products:sector-thesis`) explicitly modeled on "how established API businesses (Stripe, Twilio, Plaid-style) are built" (the spec cites *Building an API Product*, Bruno Pedro, 2024, by name) — hashed API keys, per-key product entitlements, daily rate limits, all enforced in one Edge middleware. |
| **Alternative** | Expose the internal `/api/v1/*` routes directly to partners with a simple API-key check, skipping the separate contract layer and product-entitlement model. |
| **Why chosen** | Explicitly stated: the Anti-Corruption Layer pattern (see `lib/api-contracts/v1/company.ts` in the Tier 1 guide) exists specifically so "internal storage/pipeline changes never reach a repository's callers; internal model changes never reach a partner integration" — a direct pass-through of internal routes would leak exactly the prompt/pipeline-internals detail the spec says must stay hidden (e.g. `validationScore`, `flaggedCount`, the full per-metric quote/language-shift data), and would couple partner-facing stability to internal refactoring velocity. |
| **Benefits** | A partner integration can survive internal pipeline changes untouched, as long as the contract mapping function is updated to keep producing the same external shape. Manually-provisioned keys keep the initial partner surface small and auditable (no self-serve abuse vector) while the product is still proving demand. Reuses the entire repository layer (ADR #2) rather than duplicating data access. |
| **Costs** | Real added layering (route → middleware → service → repository → contract mapper) for what is, so far, only 3 external endpoints — a meaningful amount of architecture for a low-volume, manually-onboarded partner base. The rate-limiting mechanism has a self-acknowledged race condition (see `middleware.ts`'s Tier 1 entry) accepted as good-enough at current partner volume, not fixed. |
| **Future consequences** | The architecture scales cleanly to more partners and more products (new entries in `PRODUCT_ROUTES`, new contract files) without touching the internal app — exactly the payoff the "additive, not a rewrite" design was purchased for. Self-serve billing/signup, if ever added, is a genuinely separate future project (explicitly named as out of scope), not a natural extension of this architecture — it would need its own onboarding flow, payment integration, and probably a shift from manually-hashed keys to a self-service key-issuance system. |

## 7. Hosting: Vercel → Azure App Service → Azure Container Apps (two-stage migration, only the first stage is documented)

| | |
|---|---|
| **Decision** | Move hosting off Vercel to Azure, in two stages: first to Azure App Service (fully planned, executed, and documented — `docs/superpowers/plans/2026-07-10-azure-hosting-migration.md`), then — undocumented anywhere in `docs/superpowers/` — a further move to Azure Container Apps, evidenced only by the live `Dockerfile`, `.github/workflows/deploy-azure.yml` (titled "Deploy to Azure Container Apps," pushing to `quantalyzeacr.azurecr.io` and running `az containerapp update --name quantalyze-app-ca`), and `next.config.mjs`'s retained `output: "standalone"`. |
| **Problem (stage 1)** | Per `docs/superpowers/specs/2026-07-10-azure-hosting-migration-design.md`'s Context: the app was Microsoft Partner Network / cost / Indian-AMC-BFSI-Microsoft-standardization motivated to move onto Azure generally (see ADR #11 below for the fuller data+auth story), and specifically needed to move *before* the Postgres migration so the new database could use private VNet networking from day one instead of Vercel's no-stable-outbound-IP public-access posture. |
| **Chosen approach (stage 1)** | Azure App Service (Linux, Node 22 LTS after Node 20 LTS reached end-of-life mid-project — a real deviation the plan's own Execution Record documents), Next.js `output: "standalone"`, GitHub Actions + OIDC (no stored publish-profile secret), Application Insights, DNS-based cutover with a 7-day Vercel-parallel safety window. Explicitly **not** containerized: the design doc's Out-of-scope section states "No Dockerfile / containerization — App Service's Linux/Node runtime deploys from a built artifact directly," and even names Container Apps as a *possible future step* ("if the app's runtime needs ever outgrow what App Service's Node runtime offers... Azure Container Apps (Docker-based) is the natural next step. Not needed now"). |
| **Chosen approach (stage 2, undocumented)** | The live `.github/workflows/deploy-azure.yml` shows the app now builds a Docker image via the repo-root `Dockerfile` (multi-stage: `node:22-alpine` deps → build → a `nextjs` non-root runner stage running `.next/standalone`'s `server.js`), pushes it to Azure Container Registry, and deploys via `az containerapp update` against `quantalyze-app-ca` — the "future step" the App Service design doc named as "not needed now" was, at some later point, actually taken, with no corresponding design doc in `docs/superpowers/specs/` or `plans/` to explain why or when. |
| **Alternative** | Stay on Azure App Service indefinitely (the documented plan's own stated position). |
| **Why chosen (stage 2)** | INFERRED — no evidence states the reason. Plausible triggers, per the App Service doc's own named reasons for *eventually* wanting Container Apps: portability across hosts, or the App Service Node runtime's limits being reached. Also plausible: Container Apps' more standard/portable container model and its built-in scale-to-zero/autoscaling posture may have simply become more attractive once the team had already built a working `Dockerfile` for local dev (the `Dockerfile` looks App-Service-agnostic — nothing about it is App-Service-specific) — but this is speculation, not evidenced. |
| **Benefits** | Container Apps offers finer-grained autoscaling (including scale-to-zero) and a more portable deployment artifact (a container image runs identically on any container platform, unlike an App Service-specific standalone-bundle-plus-`node server.js` startup-command workaround the App Service migration's own Execution Record had to hand-discover: "App Service 503... the standalone bundle's package.json... retains 'start': 'next start'... Azure App Service's default Node startup runs npm start... Fixed with an explicit App Service startup command"). |
| **Costs** | **The single clearest documentation-debt example in this repository**: the only Azure hosting design/plan documents that exist describe a *different, superseded* deployment target as current-and-final, complete with an Execution Record documenting real production incidents (the `npm start` 503, the SSL-certificate-ordering issue, the two-A-records GoDaddy quirk) that a reader would reasonably assume still describe today's runtime — but today's actual runtime is a Docker container on Container Apps, not App Service's Oryx-free standalone-bundle deploy. Anyone debugging a live production incident using this plan as their reference would be debugging the wrong hosting model. |
| **Future consequences** | Until a `2026-0X-XX-azure-container-apps-migration-design.md` (or equivalent) is written, this gap will keep costing whoever next needs to reason about deployment — they'll either have to reverse-engineer the actual setup from the workflow YAML and Dockerfile (as this analysis did) or, worse, trust the stale App Service doc and be wrong. |

## 8. NDJSON streaming vs. WebSockets vs. polling

| | |
|---|---|
| **Decision** | Stream pipeline progress to the browser as newline-delimited JSON over a plain `ReadableStream` HTTP response (`Content-Type: application/x-ndjson`), not WebSockets, not client-side polling. |
| **Problem** | Delta Analysis can take 15 seconds to several minutes; a plain synchronous request-response would leave the user staring at a spinner with zero feedback for that entire window, and polling would add request overhead and latency to progress updates for a feature whose whole differentiator is "watch it work in real time" (`components/AgentPanel.tsx`). |
| **Chosen approach** | The server opens a `ReadableStream`, calls `controller.enqueue()` once per progress event as `lib/pipeline.ts`'s `onProgress` callback fires, and the client (`lib/api.ts`) reads the response body via `getReader()`, buffers, splits on `\n`, and JSON-parses each complete line. |
| **Alternative** | WebSockets (bidirectional, persistent connection) or short-interval polling (`GET /status` every N seconds). |
| **Why chosen** | Explicitly stated in `TECHNICAL_ARCHITECTURE.md` §10: "Zero infrastructure overhead — works over standard HTTP," "Compatible with Vercel serverless (no persistent connections needed)," "Client can show real-time progress," "Graceful degradation: if connection drops, partial results are still usable" [server-side — the pipeline keeps running and still caches its result even if the client stream is abandoned]. |
| **Benefits** | No WebSocket gateway/connection-management infrastructure needed, works identically whether the platform is Vercel serverless or Azure Container Apps (no persistent-connection assumption either platform needs to support specially). Real per-agent progress, not just a coarse spinner. Every serverless-friendly hosting option stays available without re-architecting this feature. |
| **Costs** | One-directional only — no client→server mid-stream signal exists, so there is no "cancel this analysis" affordance; a user who navigates away doesn't stop the server-side pipeline from completing (and burning Gemini calls) on their behalf (see `app/api/v1/analyze/route.ts`'s FAILURE section in the Tier 1 guide). No automatic reconnect/resume if the connection drops mid-stream — the client-side progress state is simply lost (though the eventual cached result is not). |
| **Future consequences** | This is a durable-enough choice as long as progress is the only thing that needs to flow to the client — if a future feature needs true bidirectional interaction mid-pipeline (e.g. a user steering an in-progress multi-step agent, or a cancel button that actually stops server work), NDJSON stops being sufficient and a WebSocket or Server-Sent-Events-plus-cancel-token design becomes necessary. |

## 9. No vector database / no RAG in production, despite it being built in the archived prototype

| | |
|---|---|
| **Decision** | Ship zero retrieval-augmented generation and zero vector store in the live product; feed each pipeline call the full (truncated-to-120K-char) transcript text directly in the prompt, every time. |
| **Problem** | The archived `finance-agent/core/` (per `README_ARCHIVE.md`) built exactly this — "Ingest, parse, chunk, embed, and persist financial knowledge... semantic memory (vector store)" — as a foundational layer of the original platform. The live product doesn't use it. |
| **Chosen approach** | `MAX_TRANSCRIPT_CHARS = 120_000` in `lib/pipeline.ts` — the entire (truncated) transcript is pasted into every relevant Gemini call's prompt, no chunking, no embedding, no similarity search, no retrieval step of any kind. |
| **Alternative** | Chunk each transcript, embed the chunks into a vector store (as the archived prototype built), and retrieve only the top-k relevant chunks per query/section instead of sending the whole document every time. |
| **Why chosen** | INFERRED, but well-supported by the cost/latency data actually in this repository: `TECHNICAL_ARCHITECTURE.md` §9 puts Delta Analysis at ~600K input tokens (120K chars × 5 sections × 2 quarters) for ~$0.03 total cost, and the whole per-user monthly Gemini bill at ~$1.00-1.50 — figures only possible at Gemini 2.5 Flash Lite's stated ~$0.01/1M-input-token pricing. At that price point, and with each transcript already comfortably inside the model's context window, retrieval exists to solve two problems this product doesn't clearly have yet: (a) **cost** — full-context is already cheap enough that trimming input tokens via retrieval wouldn't materially move the unit economics (95% gross margin already claimed at 50 users, per §9); (b) **scale beyond one document** — RAG earns its complexity when a query must draw from a corpus too large to fit in context (many documents, a long history); this product's queries are scoped to one or two specific transcripts per analysis, each of which fits in context whole. A one-shot full-document read is also strictly more faithful to management's actual language for a product whose core value proposition is "verbatim quotes... do NOT paraphrase" (a directive repeated in nearly every `AGENT_PROMPTS` entry in `lib/pipeline.ts`) — retrieval risks silently dropping the exact passage a section needed, an accuracy risk this product's positioning (10x more comprehensive than incumbents) can't easily absorb. |
| **Benefits** | No vector-store infrastructure to run, embed into, keep in sync, or pay for. No retrieval-quality tuning (chunk size, overlap, top-k, re-ranking) — an entire category of AI-system tuning work this team doesn't have to do. No risk of a retrieval step silently omitting the one quote a downstream agent needed. |
| **Costs** | This approach does not scale past what fits in a model's context window — if transcripts grow meaningfully longer (very large conglomerates' multi-hour calls are already noted in a `lib/pipeline.ts` comment as running "2-3+ hours," which is exactly why the 120K-char cap exists at all) or if a future feature needs to reason across *many* transcripts/documents at once (e.g. true cross-company or historical-corpus reasoning — precisely the archived platform's ambition), this architecture has no answer beyond "truncate harder," which directly trades off against extraction completeness for exactly the largest, often most-followed companies. |
| **Future consequences** | This is very likely the right call for the product as scoped today (per-company, per-quarter or per-few-quarters analysis) and is a good example of not building the AI-engineering-fashionable thing (RAG) when the cost/latency math doesn't require it. It stops being the right call the moment the product needs genuine cross-document or cross-portfolio retrieval — which is exactly the capability the archived, frozen prototype was built toward and the live product deliberately walked away from (ADR #1). |

## 10. Frontend architecture — Server Components + Client Components split

| | |
|---|---|
| **Decision** | Use Next.js 14's App Router split deliberately: Server Components handle auth-gated page shells and redirects; Client Components (`"use client"`, e.g. `DashboardClient.tsx`, `AgentPanel.tsx`) handle everything interactive. |
| **Problem** | The app needs both server-side auth enforcement (redirect an unauthenticated user before any page content or client JS ships) and rich, stateful client interactivity (live NDJSON-driven progress panels, search-as-you-type, streaming results) — a single rendering model doesn't serve both well. |
| **Chosen approach** | Per the Azure Auth Migration design doc's own inventory: `app/page.tsx`, `app/sectors/page.tsx`, `app/screener/page.tsx`, `app/kpis/page.tsx`, `app/dashboard/page.tsx`, `app/request/page.tsx` are Server Components doing redirect gates via Auth.js's `auth()` helper; the corresponding `*Client.tsx` files (`DashboardClient.tsx`, etc.) are `"use client"` components doing all the interactive work, receiving whatever server-fetched initial data they need as props. |
| **Alternative** | A single client-side app shell (classic SPA/CSR) with auth enforced entirely client-side (redirect-after-mount), or full SSR-per-request re-fetching without the split. |
| **Why chosen** | INFERRED from the pattern, consistent with idiomatic Next.js 14 App Router usage: server-side auth gating prevents ever shipping a protected page's JS bundle (or a flash of protected content) to an unauthenticated request, which client-side-only auth checks cannot guarantee. Splitting the page shell (Server) from the interactive body (Client) keeps the server-rendered portion cheap and cacheable while concentrating the actual complexity (state, effects, streaming) where it has to live anyway — the browser. |
| **Benefits** | No protected-content flash for unauthenticated users; smaller initial client JS payload for the parts of each page that are genuinely static (nav shell, layout); a clean, consistent per-page pattern (`page.tsx` + `PageClient.tsx`) that's easy for a new engineer to learn once and reapply. |
| **Costs** | The pattern doesn't prevent the "God component" problem noted in `DashboardClient.tsx`'s Tier 1 entry — the split happens once, at the page boundary, and everything inside the client half can still grow unchecked (19 `useState` hooks in one file) without the Server/Client boundary itself offering any further decomposition discipline. |
| **Future consequences** | This split will need re-verification at each future auth-provider change (as already happened once, moving Supabase Auth → Auth.js/Entra — the Auth Migration doc explicitly enumerates all 13 call sites needing updates) — the split is sound, but every call site that reads session state is a place that auth-provider changes ripple to, and there's no single chokepoint (beyond `lib/auth.ts`'s `getCurrentUser()` wrapper, which is used inconsistently: some pages call `auth()` directly per the migration doc's file list, not the wrapper). |

## 11. The second infra pivot — full migration off Supabase to Azure-native (Postgres, Blob, Entra ID)

| | |
|---|---|
| **Decision** | Beyond moving *hosting* to Azure (ADR #7), fully replace Supabase as a platform: Postgres (Supabase-managed → Azure Database for PostgreSQL Flexible Server), Storage (Supabase Storage → Azure Blob Storage), and Auth (Supabase Auth → Microsoft Entra External ID via Auth.js) — three separate, sequenced sub-migrations, each with its own dated design doc. |
| **Problem** | Per `docs/superpowers/specs/2026-07-10-azure-data-storage-migration-design.md`'s Context: the decision to move to Azure at all was made 2026-07-09 for stated reasons of "Microsoft Partner Network status, cost, and — the decisive factor — that Indian AMC/BFSI back-office IT is disproportionately Microsoft-standardized, which matters for vendor security reviews and Entra ID SSO federation if this product is ever sold into an AMC's environment." This is a go-to-market-driven infrastructure decision, not a technical one — the product's actual enterprise buyers (asset management companies) run Microsoft-centric IT and will vendor-security-review a Microsoft-native stack more favorably. |
| **Chosen approach** | Sequenced deliberately — Hosting first (a prerequisite, not a follow-on: Vercel's serverless functions have no stable outbound IPs, so a database reachable from Vercel had no choice but public-access networking; moving hosting to Azure first meant the new Postgres server never needed public exposure at all, going straight to private VNet-only access) → Data+Storage (12 repository implementations swapped behind already-existing interfaces, per ADR #2's payoff) → Auth (last, because it was the one Supabase surface with *no* existing abstraction — `@supabase/ssr` used directly in ~14 files — and because it depends on neither of the other two). |
| **Alternative** | Stay on Supabase indefinitely, or migrate all three surfaces (hosting, data, auth) simultaneously in one larger cutover. |
| **Why chosen** | Explicitly stated (see Problem above) — an enterprise sales/security-review motivation, not a performance or cost-driven one on its own, though cost is named as a secondary factor. The sequencing rationale is also explicit, not inferred: "Doing hosting first means this spec's Postgres server never needs public exposure at all... a strictly worse security posture than the private/VNet access Azure-to-Azure traffic can use, and one that would just be thrown away the moment hosting moves anyway." |
| **Benefits** | A genuinely more defensible security posture for an eventual AMC sale (private VNet-only Postgres, no public database endpoint ever created). The repository-pattern investment (ADR #2) paid for itself here concretely — the Data+Storage cutover's own design doc states the invariant list plainly: repository interfaces, domain entities, the service layer, public API contracts, and route handlers all stayed unchanged; only implementations and the composition root moved. Real production issues were found and fixed during execution and are now documented in-code as durable knowledge (e.g. `lib/postgres/client.ts`'s keepalive/connectionTimeout tuning for Azure VNet's connection-reaping behavior; `auth.ts`'s `profile.oid`-vs-`account.providerAccountId` UUID-shape fix). |
| **Costs** | Genuinely difficult, hand-discovered production issues along the way — none catchable by TypeScript, all found only by testing the real deployment: the App Service `npm start` 503 (ADR #7), the Postgres idle-connection ECONNRESET pattern on Azure's VNet path, the Entra `oid`-vs-`sub` UUID mismatch that broke every credits/analysis query. A `WatchlistRepository` security-model change was forced (RLS-based authorization, which had no raw-Postgres equivalent, replaced with explicit application-level `WHERE user_id = $1` filtering) — a real, if narrow, security-model change made under migration pressure rather than as a standalone security review. And, as ADR #7 and the tech-debt log both document: **the top-level README.md, TECHNICAL_ARCHITECTURE.md, and .env.local.example were never updated** — they still describe a fully-Supabase system, weeks to months after the code moved on. |
| **Future consequences** | The migration itself is a clean execution of the Strangler Fig pattern this codebase clearly favors (see ADR #2), and each sub-migration documents its own rollback plan and safety window — genuinely mature process for a small, pre-launch team. But the failure to update the top-level docs after each cutover is now this repository's single largest "trust the docs at your own risk" liability (see `20_TECHNICAL_DEBT_AND_GAPS.md`) — every future engineer's first read of `README.md`/`TECHNICAL_ARCHITECTURE.md` will describe infrastructure that no longer exists, and only reading the dated `docs/superpowers/` planning docs (or the code itself) reveals the truth. |
